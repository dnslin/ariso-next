## 4. 任务与依赖规则

任务分为规格、设计、实现和验收。每个任务只有一个明确的主要交付结果，默认按一个可独立评审的 PR 拆分。共享迁移、锁文件和接口变更按真实改动边界协调。

每项实施任务必须包含：稳定 ID、PRD 条目、所属模块/里程碑、已评审规格、范围与非范围、直接前置任务、预计文件、可观察验收条件、实际验证命令、设计引用或无界面理由。

状态规则：

1. `Draft`：需求、规格、设计或任务验收尚未明确，不能实施。
2. `Blocked`：任务已明确，但任一必需前置未完成；可以做独立调研，不实施依赖尚未交付内容的任务。
3. `Ready`：全部直接前置为 Done，所需规格及设计已评审，验证方法可执行。
4. `In progress` / `Review`：实施中或等待评审；代码存在、PR 已开都不等于完成。
5. `Done`：全部前置仍为 Done，交付已合并或文档/设计已验收，任务自身验收与相关检查通过，证据可追溯。

“Issue 已关闭”必须核对完成原因和交付证据；取消或重复关闭不能满足前置条件。前置重新打开或发生影响下游的契约变更时，下游重新检查依赖与验收，不能沿用失效的完成结论。

任务索引保存直接依赖，反向依赖由同一份关系计算，避免两套手工关系不一致。生成任务时检查缺失 ID、自依赖、循环依赖以及需求遗漏。

GitHub 用作执行状态来源。本地保留任务定义与链接索引，不再长期维护另一套完成勾选。准备阶段 ID 尚未同步 GitHub，不能把它们当成现有 Issue 编号。创建时核实并使用可用的依赖关联；PR 合并前逐项检查前置。当前仓库尚无依赖自动拦截检查，本文规则不能被描述为已经自动强制执行。

后续需交付一个针对明确任务 ID 和前置关系的轻量依赖检查，接入所需 PR 检查；同时核实仓库是否实际启用对应合并规则。规则启用前明确记录为人工执行，不声称 GitHub 会自动阻止关闭 Issue。检查设计与实施归 P2-DEPENDENCIES。

前端和后端拆成独立任务时，先完成接口约定；使用模拟数据的界面任务只能验收界面本身。用户可用功能任务必须依赖真实接口和界面集成，不能以模拟结果关闭。
