## 三项队列相关失败的完整因果链

1. `default/server.log:46`，14:28:13.992Z 接受 M2 重启恢复图片 `6c2e6fba-b8b4-4deb-bc3c-9310591a414d`；`:47` 正常 runtime shutdown；`:54` 重启后 identify 失败。
2. 直接原因是 `ps -axww` 超过硬编码 1000ms，产生 `MEDIA_TOOL_SHUTDOWN_FAILED`。`src/server/media/tools.ts:12-20` 定义这一超时与错误。`:151-154` 在媒体子进程正常完成后也执行 terminate/group inspection，因此错误可在实际工具完成后的清理中发生。
3. `src/server/media/queue.ts:188-196` 对这种 settlement 错误保存 failure，abort 整个 queue controller。后续上传仍可被 receiver 接受，queue 不再 claim 工作。
4. `server.log:56-59` 记录互动和连续性上传被接受；直到 account runtime 重启后的 `:66-73`，同一批图片才进入 metadata 并完成。
5. 因此三个超时有同一个具体产品运行时故障；不能一律归为“浏览器环境”。日志中有并发任务进程，资源争用是可能触发因素，但没有 CPU/调度时长采样，不能证明资源争用是唯一原因。

## 四项 URL 失败的完整因果链

`src/app/library/use-library-query.ts:140-154` 明确实现：已保存分页偏好且 URL 无 page 时，history.replaceState 补 `page=1`。图库和相册详情共用这条路径。完整流程前面图库用例设过此偏好；偏好跨同一个 origin/page 仍存在。四项原错误里的实际 URL 都是相同目标 path 加 `?page=1`，页面内容已渲染。其断言要求完整字符串不带 query，与当前产品合同冲突。这些模块不在 Issue 193 产品 diff 中。本次仅报告，不改范围外场景。
