## 已修复发现

**P2：清理任务受理后的列表刷新失败未进入可恢复错误状态。**

`TrashScreen` 原先向单图清理、批量永久删除与批量恢复控制器传入默认 `client.invalidateQueries({ queryKey: ['trash'] })`。TanStack Query 的默认刷新 Promise 在请求失败时仍正常完成。控制器依赖 Promise 拒绝设置 `refreshError`，因此实际组合页无法显示其刷新失败与重试入口。单图清理页同时只展示详情读取错误，会隐藏后台列表刷新失败。

用本项目依赖与 Node 24 做最小复现：建立活跃的 `QueryObserver`，先成功读一次 `['trash']`，再令查询函数抛出 `HTTP 500`，分别调用默认刷新与第二参数 `{ throwOnError: true }` 的刷新。实际输出：

```text
default invalidate resolved; query error: HTTP 500
throwOnError invalidate rejected: HTTP 500
```

实现者已将上述三个控制器的 `onRefresh` 回调改为传入 `{ throwOnError: true }`。已复核该调用与控制器的捕捉、保留任务状态和重试逻辑相符。未承接可恢复错误状态的普通 `void invalidateQueries` 保持默认行为，避免引入未捕获 Promise 拒绝。

此复现只证明实际依赖行为与修复方向。组合页的错误可见性仍由本轮真实浏览器场景取得证据。
