## 结构判断

| 审阅点                 | 判断与依据                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 删除重复退出确认       | `session-controls.tsx:79–87` 删除额外 GET，保留 POST 失败分支和显式目的地。`src/server/identity/auth.ts:334–345` 已负责在成功响应前核对原 Cookie 的会话撤销；原有集成用例覆盖读取/删除失败。客户端复用这个真实契约，直接减少一次串行请求和一种“已退出但页面仍报错”的中间状态。这里删除复杂度比引入重试或限流例外更合适。 |
| GitHub 焦点意图        | `use-github-account-view.ts:32、48–54、99–105` 只保留一个瞬时布尔意图，并在查询对应视图可用后消费。配置按钮由 `github-account.tsx:98–125` 的相同就绪条件决定。该意图不属于服务器数据，不进入查询缓存，也不引入新的可见业务状态。使用 ref 避免为 DOM 回焦另设一轮状态更新。                                               |
| SMTP 焦点提交          | `use-smtp-page.ts:108–120、200–207` 将原延迟帧回调替换为提交后的同步布局副作用。回焦意图只消费一次；当前操作不空闲时不消费。没有待取消的生产计时器或帧回调。四个既有调用点仍位于邮件设置所属 hook，复用原控件/标题回退，不修改通用外壳或 HeroUI。                                                                        |
| 无依赖数组的布局副作用 | `use-smtp-page.ts:110–120` 每次提交只检查空闲状态和待消费 ref；没有意图时立即返回。关闭弹窗也需要在 `operation` 不变时处理意图，因此只依赖 `operation` 会漏掉该调用路径。当前写法省去额外计数 state 或人为触发器，成本为常数级；未发现需要泛化的性能问题。                                                               |
| 两种焦点路径是否应合并 | GitHub 依赖 TanStack 查询就绪及替换控件；SMTP 依赖操作空闲、弹窗关闭及原控件禁用状态。二者只共享最终 `.focus()`，不存在值得新增通用 hook 的共同业务模型。抽象合并会把各模块的就绪条件和目标策略带入新层，增加概念数。保留两个局部实现更清楚。                                                                            |
| 事件与副作用职责       | 网络调用、保存值更新、通知仍在用户事件处理器中；新增 effect 仅负责必须等待 DOM 提交的焦点操作，没有将网络行为迁入 effect。这符合 React 技能中事件归属及瞬时 ref 的边界。                                                                                                                                                 |
| 类型与数据规模         | 新增生产字段仅为 `boolean` 和 `string \| null` ref；没有扩大 API、缓存或快照数据。原有 `PendingWrite`、请求模型和权限边界未改。未引入生产 `any`、类型强转、配置层或依赖。SMTP 目标字符串来自局部调用点，不接受外部输入。                                                                                                 |
| 浏览器回归辅助层       | `e2e/smtp-focus.mjs:1–108` 复用 `smtp-page` 与 `smtp-transport`，独立承担一项保存/继续编辑竞态，没有把帧故障逻辑塞入共享运行器或原运输辅助方法。实际 HTTP 结果保持不变，仅延迟交付与回调。新的帧状态只保存原 API 和当前回调，未复制页面业务对象。                                                                        |
| 故障注入生命周期       | `e2e/smtp-focus.mjs:16–25、34–52、104–107` 在释放时先恢复帧 API 并删除临时状态，再执行本次暂存回调；正常完成和异常路径均安排释放与运输层恢复。没有新进程、后台定时器或需要生产清理的全局状态。                                                                                                                           |
| 默认与定向入口         | `package.json` → `scripts/verify-browser.mjs` → `scripts/browser-plan.mjs` → `e2e/smtp.mjs:212–225` → `smtp-focus.mjs` 的归属清楚。默认 full 和 SMTP interactions 都进入新增案例；`focus` 仅是 SMTP 的合法 phase，没有广播到其他 suite。两个运行计划测试分别断言阶段选择和配置传递。                                     |
| 单元辅助模型           | GitHub 沿用现有测试 harness；SMTP 局部 `Hooks` 仅模拟保留状态、回调依赖和明确提交顺序；session harness 仅模拟当前退出/背景读取所需的状态与初始 effect。测试中的 `unknown`、强转和 DOM 替身局限在辅助层，未渗入产品。没有现成正式的公共 hook 测试工具可直接复用；为了本次窄验证新增通用 React 模拟框架反而会扩大维护面。  |
| 测试模型的证明范围     | SMTP harness 将 `useEffect` / `useLayoutEffect` 同步到受控提交，不能证明真实 React 调度；GitHub 替身也不能证明 TanStack 的全部通知次序。当前证据明确标注这些限制，另有真实浏览器定向结果。没有用模型测试取代浏览器或将一次定向通过扩展为 full/SMTP 协议矩阵通过。                                                        |
