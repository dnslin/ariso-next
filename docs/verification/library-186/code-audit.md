## 已核对的行为

- 仅有效所有者入口可执行批量命令，原路由权限与来源检查保持不变；输入明确 IDs、规范化查询与范围，每请求最多 200 项。重处理命令要求每个选中图对应唯一 UUID，不能附带额外任务身份。
- `batch.ts` 逐图事务与让出执行时间复用既有模式，异常回滚当前图并继续其他项。复用 `requestReprocess` 进行真实状态、活动任务、处理开关、格式适用性与首次失败限制检查。
- 每图受理时创建不可变 media 设置快照。没有跨请求整批快照，也没有在数据库事务中执行图片工具或网络操作。
- 返回 `accepted` 与真实任务摘要；按本次 UUID 检查图、任务种类与范围，不把另一个较新任务当成本次结果。`check` 不创建任务，未找到时返回 `unknown`，同 UUID 已存在时不重复受理。
- 旧已发布版本由现有 media 生命周期保留，批量受理不提前修改版本指针。生成候选和处理完成分别表达。
- 客户端分批固定显式 IDs，逐块裁剪 taskIds；响应丢失停止后续块，并保留未知与未发送项。已受理项从选择移除，执行失败提供独立显式重试。
- 范围、结果使用 HeroUI 组合，公共 OwnerShell 与返回控件复用；未复制导航。进度读取只包含 queued/running 的本次任务，关闭、卸载与错误清理计时器/请求，不取消服务器任务。

## 明确保留的未知结果边界

本次持久身份属于 media 任务，未受理的拒绝结果没有另存批量凭据。原 apply 响应丢失且该图片实际未受理时，后续只读 `check` 可能持续返回 `unknown`，因为原 UUID 不存在。此时不能从“没查到”推断请求已经结束，也不能把另一个最新任务当成本次结果。

实现保持本次 UUID 与待核对说明，不自动或伪装成只读地重新写入。这符合 library §7 的“不能核实时显示结果待核对”边界，但不能声称所有失落响应都能恢复为已完成或可重试。对原 UUID 显式重新尝试受理可以避免重复任务，却可能把原拒绝项按新的设置受理，属于新的用户行为，未纳入本次实现；没有为此引入批量任务引擎。

审计者实际执行 `git diff --check`（通过）与 `pnpm exec prettier docs/verification/library-186/code-audit.md --write`（通过），未运行重复全量业务检查。后续若集成/浏览器出现本次实现问题，必须修复并重跑受影响项；代码审计通过不是创建正式待评审 PR 或人工 UI 完成的替代条件。
