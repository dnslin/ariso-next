## 1. 建议结论

增加一个面向图库的轻量图片编辑器：打开已上传图片，框选需要遮挡的位置，添加文字或 Logo 水印，然后保存。多张图片使用同一套编辑参数，并允许逐张调整。

它主要解决两个现有流程没有覆盖的问题：截图中的姓名、账号等位置需要局部遮挡；一组图片需要使用相同的署名、Logo 或固定版式。编辑入口独立于全站处理设置，不要求用户为了改一张图片而修改以后所有上传的规则。

推荐浏览器使用 **Konva + react-konva** 提供画布交互，服务器复用现有 **ImageMagick** 生成最终图片。模板保存业务参数，不保存某个画布库的内部对象树。所有保存结果都将打码和自定义水印写进实际图片像素。

## 4. 单张编辑流程

入口放在图片详情的“编辑图片”。上传完成项提供同一入口；仅在图片处理完成并满足编辑条件后可用，不在上传结束时强制打开。

流程：**打开图片 → 打码或加水印 → 查看最终效果 → 另存新图 / 覆盖原图 → 查看保存结果。**

- 桌面：顶部工具与撤销/重做，中间画布，右侧当前工具参数，底部保存方式与保存按钮。
- 手机：独立全屏编辑页，画布占主要空间，底部工具栏与可展开参数面板。保存操作沿用项目固定底栏规则。
- 画布支持直接操作，参数面板同时提供位置、大小、颜色等精确输入。键盘用户可选择区域、调整位置、删除对象与撤销，不能把全部能力限制在拖动操作上。
- 编辑器始终从当前 `original` 内容开始，自动纠正照片方向；不能把详情缩略图或已有水印派生图当作底图。
- 普通拖动提供本地即时预览；明确的“最终效果”由服务器使用正式渲染流程生成。保存与最终预览使用同一套编辑参数，过期预览响应不覆盖当前画面。
- 未保存修改离开时提示；服务器已受理的保存任务不因关闭页面自动取消。重新进入能读取真实结果，不能只依赖浏览器内存判断成功。

### 4.1 另存新图（已确认的默认方式）

建议新图与源图使用同一存储，名称增加“编辑”后缀，继承可见性、相册与标签。新图拥有独立 ID、创建时间和统计，不继承源图的分享授权。以上继承细节仍属本提案建议。

**另存不会修改源图及其现有链接。** 在保存方式旁说明这一点。用户要遮挡已发布原图时，应选择覆盖或另行处理源图，不能因新图已打码就提示原内容已撤回。

另存是明确创建新资产的动作，建议不套用普通上传“重复文件跳过”的行为。没有任何编辑操作时禁用保存，避免把编辑入口变成普通重复上传入口。

### 4.2 覆盖原图

保持图片 ID、现有链接、显示名、可见性、相册、标签和创建时间。将编辑结果作为新原图，再按现有替换规则重建已经发布的派生版本与尺寸产物，全部成功后一起切换；失败仍显示旧内容。继续更新指纹、元数据、内容更新时间及既有临时分享撤销状态。

在保存区说明“将更新已有链接中的图片，不提供历史回滚”。选择保存方式并点击保存即为明确提交，不额外增加多层确认弹窗。

覆盖后系统发布的新版本都必须从打码后的新原图生成，不能保留某个仍显示未打码内容的派生版本。已经下载的文件和站外缓存不会因此被收回，旧对象清理也继续遵守现有可观察流程。

### 4.3 与站点自动水印的关系

编辑器中的水印是本次图片内容的一部分；现有站点水印仍是派生版本规则。另存按提交时的处理设置生成派生图，覆盖按已发布版本的历史配方重建。模板不会修改全站水印设置。

因此，若站点还会生成水印版本，可能在编辑结果上继续添加站点水印。最终预览应能查看编辑后原图及实际水印版本，明确展示叠加结果，不暗中关闭站点规则。若未来要让单张图片覆盖站点水印规则，需要另行明确版本语义。

保存后再次打开，编辑的是已经合成的图片；只能撤销当前会话的新操作。保留原始可编辑工程、任意移除过去水印和打码，不纳入本轮。

## 5. 模板与批量处理

模板是一组可重复使用的编辑参数。例如“右下角 Ariso Logo，宽度占图片 15%，透明度 40%”，或者“遮挡同款截图顶部的账号区域”。不是直接复制上一张图的固定像素坐标。

### 5.1 模板包含什么

- 模板名称、打码区域、水印参数与所需素材 ID。不包含源图、相册、标签、图片可见性或保存方式。
- 打码区域采用图片中的相对坐标。水印优先用锚点定位，例如右下角，再保存相对边距与大小。自由拖动后同步更新对应参数。
- 水印字号、马赛克颗粒和边距使用约定的相对尺度，应用时转换成目标图片像素。像素取整规则由前后端共享；遮挡区域边界不能因取整留下原内容细线。
- 创建模板时默认包含水印，打码区域需要主动选入。允许只存打码模板。
- 模板删除或修改不影响已经保存的图片。已提交任务使用提交时的参数与素材快照，不受后续模板修改影响。

### 5.2 多张套用流程

**图库选中多张 → 编辑图片 → 选择模板 → 查看每张预览 → 必要时微调 → 批量保存 → 逐项查看结果。**

水印按每张图的尺寸、方向和边缘位置计算。打码模板只能解决版式相近的图片；同一相对位置不代表同一个人脸、账号或文字。包含打码区域时，逐张展示检查状态，未检查的图片不能直接作为已完成隐私处理提交。

单张微调只影响当前批次的这张图片，不自动修改模板。批量保存方式同样默认另存新图。批次中的不支持格式、回收状态、停用存储或任务冲突逐张说明，不静默跳过。

复用现有媒体队列并发，按单张任务执行。部分失败不回滚已成功图片；结果保留“成功、失败、尚未提交/已取消”的清单。重试只提交明确失败项。响应丢失先查询任务状态，防止另存时重复生成副本。

首版不增加独立批量任务服务，也不承诺关机后继续尚未提交的浏览器批次。已经被服务器受理的单张任务沿用持久任务恢复规则。

## 7. 技术边界建议

### 7.1 数据流与模块责任

1. 所有者打开编辑器，服务器返回当前原图对象标识、纠正方向后的尺寸和可编辑条件。
2. 浏览器通过受鉴权的同源读取入口取得预览底图，不直接依赖 S3 公共地址或把私有图片交给外部服务。
3. 用户操作更新共享的 `EditRecipe` 业务参数；Konva 根据参数显示选框与效果。
4. 服务器读取当前原图，纠正方向，先打码、再叠加自定义水印，生成新的图片文件；正式保存使用完整像素，不能把缩小的预览导出当成原图。
5. 另存调用内部图片入库能力；覆盖调用现有候选发布能力。处理器不向自己的 HTTP 上传接口绕行。
6. 按现有队列查询结果、清理候选与临时文件，并通知图库更新。

`library` 负责入口、选择与批量反馈；`media` 负责配方、模板、渲染与发布；`storage` 继续负责 Local/S3。编辑器按需加载，不加入普通图库首屏资源。既有 HeroUI、Tailwind、Lucide/Gravity 用于周边控件，画布库只负责画布。

### 7.2 最小数据扩展

- 共享编辑参数放在 `src/shared/`，包含规范化后的区域、水印与输出参数；位置基于纠正方向后的图片画布，不使用浏览器窗口坐标。
- 模板增加一张表，保存名称、配方、创建/更新时间，并纳入现有水印素材引用与备份范围。
- 编辑执行扩展既有 `media_jobs`；必要的源对象、保存模式、结果图片 ID 和不可变配方放在对应任务载荷中。实施时按现有 schema 风格决定载荷的具体存放位置，不新建第二套队列。
- 活动任务持有源对象和素材引用，完成后按现有清理规则释放。任务记录不成为永久保留旧原图的隐形历史版本库。
- 编辑器提交打开时的原图对象标识。提交时若原图已被另一操作替换，返回明确冲突并要求重新加载，防止旧画布覆盖新内容。复用实际对象身份，不额外发明签名或锁系统。
- 复用当前所有者授权、任务冲突、备份暂停、资源预算、取消和日志边界；不新增权限体系、工作进程或任意远程图片抓取功能。

编辑 HTTP 需要覆盖“读取编辑上下文、生成最终预览、提交保存、查询结果”和模板增删改查。具体 URL、字段及错误码在范围批准后写入正式契约；本提案不将示意接口当成已经存在的能力。

| 4. 覆盖原图           | 完整接入候选发布和既有版本重建                           | ID/关联保留；所有现有版本及尺寸一起切换；失败保留旧图；指纹、元数据、分享与缓存行为正确 |

| 6. 批量应用           | 选多图、逐张预览/微调、批量另存或覆盖、失败重试          | 打码检查状态；不支持项明确；部分失败与结果不明可区分；不重复保存成功项                  |

每一步都补充相关单元、真实媒体集成与真实页面验证，完成一个可工作的流程后再扩展。第一步若发现 Konva 无法满足必要交互，再依据具体缺口评估 Fabric，不同时建设两个实现。

### 8.1 必须验证的行为

- 打码真实改变结果文件；纯色遮挡不透明；马赛克与纯色都覆盖选区边缘。不能用 CSS 遮挡或可移除的展示层冒充保存结果，也不能承诺低强度马赛克绝对无法辨认。
- 原图、压缩、缩略、水印、已有尺寸及下载都读取预期版本；覆盖失败和服务器重启不发布半成品。
- 方向标签、透明度、极端横竖比例、小图、中文、平铺、矩形重叠与边缘区域有真实样本。前后端像素取整和字体尺寸有对应断言。
- 模板修改不改变已受理任务；模板素材仍被引用时不被清理；删除和恢复后引用正确。
- 同时编辑/替换、停用存储、回收、备份暂停、磁盘不足、处理错误、响应丢失和部分批量失败沿用现有可观察行为。
- 按[前端共用验收](../guides/verification.md#前端共用验收)覆盖桌面/手机、浅深色、短视口、键盘和适用状态，并提供正式页面与批准设计的对照证据。
