## 1. 结论与确认状态

建议把智能集合实现为图库的已保存查询，把重复检测接入现有上传接收和图片入库流程。两项可以独立交付，不需要新服务、搜索引擎或对象去重系统。

用户已确认：

1. “截图”使用现有标签体系中的“截图”标签，不根据文件名、PNG 格式或剪贴板来源猜测。
2. 原文件内容完全相同时，默认跳过新建图片，提示查看已有图片。
3. “最近”默认采用滚动 7 天，即本次查询时刻向前 7×24 小时。
4. API / PicGo 遇到完全重复文件时明确报错，不自动返回已有图片链接。

以下首版范围随本方案与原型一并获准实施：

- 相对时间条件允许用户改为其他天数。
- “超过 10 MB”采用严格大于 10,000,000 字节；不等同于 10 MiB。
- 首版不提供“仍然上传一份”。
- 智能集合只供所有者整理图片；不增加集合分享、手动成员或自动移动文件。
- 显式替换图片保留原有图片身份和外链语义，只维护正确的当前原图指纹，不扩展为全库内容唯一限制。

| 需求标识                    | 责任                                                      | 直接复用                                                  | 两项之间的依赖 |
| --------------------------- | --------------------------------------------------------- | --------------------------------------------------------- | -------------- |
| `smart-collections`         | `library` 保存和执行查询规则，展示匹配结果                | 现有 `collections` 标签/相册、图库筛选/分页/选择/批量操作 | 无             |
| `exact-duplicate-detection` | `media` 提供原图指纹与查询；`upload` 判重、结束会话并反馈 | 接收流、SQLite 写事务、对象清理、持久任务调度             | 无             |

这两个标识用于本次需求追踪，不新增顶层业务模块。建议先交付智能集合，再交付重复检测；重复检测的并发与历史补齐风险应在开发前期验证。

## 3. 智能集合

### 3.1 产品语义

一个智能集合保存“名称、筛选条件、排序”。每次查询时从当前图库计算结果，不保存成员清单，也不向普通相册写入成员。

同一张图片可以出现在多个集合中，不复制原文件。修改标签、成功替换原图、回收或恢复图片后，匹配结果随数据变化。删除集合只删除保存的条件。

首版提供三个可应用并保存的模板，不强制创建系统集合：

| 模板              | 规则                                            | 可观察行为                                                              |
| ----------------- | ----------------------------------------------- | ----------------------------------------------------------------------- |
| 没有标签的图片    | 当前没有任何标签关联                            | 上传无标签图后匹配；添加任一标签后退出；移除最后一个标签后重新匹配      |
| 最近上传的截图    | 含选定的“截图”标签，且首次上传时间处于最近 7 天 | 保存标签 ID；标签改名仍有效；旧图今天被标记为截图，不会因此成为最近上传 |
| 超过 10 MB 的原图 | 当前原文件字节数 > 10,000,000                   | 等于阈值不匹配；压缩和加水印不改变归属；成功替换后按新原图大小计算      |

“截图”标签不存在时，模板要求选择或明确创建标签后保存，不暗中创建，也不把没有标签解释成“没有截图”。卡片目前使用 MiB 显示大小，筛选控件须明确标注 MB 及字节换算，避免阈值与卡片显示造成误解。

### 3.2 条件范围

首版保存现有图库筛选，并增加三个必要条件：标签为空、最近 N 天、原图大小大于/小于指定值。不同类别条件全部满足；同一标签条件内的多个标签沿用当前“包含任一”语义。

- 不增加嵌套 AND/OR、脚本规则、正则或视觉内容识别。
- “无标签”与“包含指定标签”互斥；相对时间与绝对日期范围互斥。界面切换条件时清楚替换原值，服务端拒绝矛盾输入。
- 查询默认沿用正常图库范围：排除回收和正在永久删除的图片；公开、私有、处理中、失败及停用存储中的图片仍可匹配，继续显示真实状态。
- 保存业务条件与排序，不保存页码、游标、已选图片或一次浏览解析出的绝对时间。
- 标签、相册、存储引用绑定 ID。对象被删除时保留规则并提示修复，不能静默去掉条件或自动绑定同名新对象。

### 3.3 界面与操作

入口放在现有图库中：标题区增加“全部图片 / 智能集合”选择菜单，条件条提供“保存为智能集合”。保持已有侧栏结构，不把每个集合塞进公共导航。

**创建：** 添加条件 → 查看实际结果 → 点击“保存为智能集合” → 输入名称 → 保存。名称表单展示条件摘要，不重建整组筛选弹窗。

**使用：** 选择集合 → 复用现有图片列表和条件条。支持网格、瀑布流、大图查看与现有批量操作；不增加“加入集合”“移出集合”按钮。

**修改：** 调整条件后显示“未保存更改”，提供“保存更改”和“另存为”。未保存前不覆盖原集合；更名、删除放在集合操作菜单中。保存失败保留输入。

**空与错误：** 无匹配结果时显示当前条件和“调整条件”；缺失引用明确指出失效的标签、相册或存储。删除集合的确认文案只说明删除规则、保留图片。

建议使用可直接访问的 `/library/collections/{id}` 表示已保存集合。集合入口仍高亮“图库”；没有另建图片详情、选择或批量操作体系。

### 3.4 “自动进入”的准确含义

自动归属表示无需手工加入或运行整理任务。打开集合、主动刷新以及现有变更刷新链路触发查询时，服务端根据最新数据重新计算。

在屏期间沿用现有设计：跨窗口真实变更通过刷新图标提示，不定时重排用户正在选择的列表。同页上传继续复用当前数据重读路径。相对时间过期在下一次打开或用户主动刷新时体现，不承诺页面静置时逐秒退出。

“最近 7 天”按已确认的滚动时间定义为本次查询时刻向前 7×24 小时。只有打开集合或用户主动刷新才重新解析下界；同一次浏览的分页、邻居、选择核对和批量请求沿用这一绝对下界，不能每页重新取当前时间。

上传、处理完成及批量操作后的数据重读沿用本次浏览边界，核对并保留仍有效的选择。只有条件、排序或时间边界使查询身份实际改变时才清空选择，不能让后台完成通知不断清空用户的选集。重新进入集合时须查询当前结果，不能直接复用无限期旧缓存。

批量操作继续使用已经选中的明确图片 ID。新进入集合的图片不自动加入选集；给“无标签”图片加标签后，应从结果和选集中退出，但不能因此改变同批剩余图片的处理范围。

### 3.5 最小数据与代码边界

建议在 `library` 内增加 `smart_collections` 表，字段仅需 `id`、`name`、`filters`、`sort`、`createdAt`、`updatedAt`。`filters` 使用受现有 Zod 查询模型约束的结构化数据，不存 SQL，也不增加通用规则引擎。

- `library` 负责保存/更名/更新/删除规则及执行查询，不让现有 `collections` 反向依赖图库筛选实现。
- 共用 `query-schema.ts` 与 `query-predicate.ts`，让列表、数量、邻居、选择核对和批量后的归属判断保持一致。
- 继续使用现有标签/相册 ID 校验和 `LIBRARY_STALE_REFERENCE` 语义。
- 标签删除、使规则失效的相册/存储删除及集合规则修改，接入现有图库变更通知与缓存失效。当前标签管理没有完整通知这条链路，需补齐相应消费处，不新增事件系统。
- 新入口使用所有者会话；备份保存规则，恢复后引用原有 ID。未来实现时检查新表是否纳入备份的实体统计和归整逻辑，不能只假设数据库快照即代表验收完成。

当前 `SPEC-library` 的“不新增业务数据表”是原有边界。若采用此方案，应明确修订为允许持久保存查询定义；不借机增加第二份图片索引或后台归类队列。

## 4. 完全重复图片检测

### 4.1 判断标准

比较接收到的完整原文件字节，使用 SHA-256 内容指纹。SHA-256 是从文件内容算出的固定长度摘要；同一原文件改名后仍会得到相同摘要。

同名但内容不同可以上传。视觉相同但重新压缩、转格式、裁剪或修改 EXIF 后，文件字节不同，首版不视为重复。不计算缩略图、压缩图或水印图的指纹来代替原图。

建议在当前站点全部存储中查找相同当前原图。选择不同相册、标签或存储位置不会绕过普通上传判重。

### 4.2 Web 用户流程

选择图片 → 传输原文件 → 检查重复 → 新图片继续处理，重复图片结束本项并显示“已跳过，图片已存在”。批量队列继续处理其他文件，不为每个重复项弹窗。

重复行提供“查看已有图片”，通过既有详情展示已有图片。它是独立终态，不显示“新增成功”，也不进入失败项自动重试。

提交结果分别汇总“新增成功 / 重复跳过 / 失败”。本次选择的相册、标签、公开性与处理设置不会自动改到已有图片上；需要调整时，通过已有图片详情完成。

首版可以避免新增重复记录、长期存储和重复派生处理，但通常仍需传输完整文件才能由服务端确认。文案采用“已存在，未新增”，不宣称“零上传流量”。浏览器计算指纹后预检查可另行评估，不作为本版前置。

### 4.3 已有图片状态

| 命中对象                                   | 建议行为                                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------------- |
| 正常图片                                   | 跳过，查看已有图片；保持原名称、可见性、关系和原图                                 |
| 等待处理、处理中或处理失败，且已有当前原图 | 跳过，展示真实处理状态；已有重处理入口负责重试，不复制图片                         |
| 回收站图片，尚未开始永久删除               | 跳过，提示“回收站已有相同图片”，进入现有回收记录；恢复由用户明确执行               |
| 存储停用                                   | 仍能识别已有记录并说明存储状态，不自动复制到新存储                                 |
| 正在永久删除或删除清理失败                 | 不作为可复用图片阻止新上传；继续保留旧清理任务及真实占用                           |
| 多张历史重复图片                           | 保留全部旧记录；优先提供正常图库中的一张，其次回收站，组内按创建时间和 ID 确定顺序 |
| 已经永久删除                               | 没有当前图片可命中，允许新上传                                                     |

查重不是历史清理功能。首版不自动合并旧图片、删除重复文件或改写已有外链。

### 4.4 指纹、并发与清理

1. 本地、中转和 API 接收时，在原始文件流上计算指纹。S3 直传在现有条件 GET 流中计算。仅完整接收成功的文件有有效指纹，不新增第二次完整读取。
2. 上传会话暂存指纹；持久指纹建议放在原图对应的 `media_objects` 记录上。判重只查 `media_versions.kind = original` 当前引用的对象，排除替换后的旧原图和候选对象。
3. 正式对象写入前先查一次，常见重复可直接结束并清理临时文件。
4. 最终 `acceptSession` 的 SQLite 短写事务内再次查询，没有命中才一起创建图片、原图引用、处理任务和集合关系。两次检查分别负责减少 I/O 和拦截并发竞态。
5. 并发请求已经各自写出正式候选对象时，后到者记录重复终态，由现有上传清理账本清理自己的对象。不能删除命中的已有文件，也不能创建额外媒体任务。

指纹使用普通索引，不加全库唯一约束。旧库可能已有重复，显式替换也可能有意让不同外链指向同样内容。无需全局锁、指纹预占表或文件引用计数。

重复终态沿用上传会话的恢复和有限清理重试。中断的待清理项在重启后继续；重试耗尽时保留对象坐标与失败原因，等待用户手动重试，不因重启重置预算。实际清理完成前仍计入相应暂存占用。一次完成请求重试应读回同一重复结果，不重新创建图片。

### 4.5 旧图库与替换图片

当前旧图片没有指纹。建议复用媒体持久任务的调度、取消与恢复能力，增加明确的指纹补齐工作类型，分批、低并发读取每个当前原图，不重建缩略图或重读拍摄元数据。

读取总量约等于当前原图总字节数；S3 还会产生 GET 和下载流量。使用已有流式读取接口，不把整个文件读入内存。显示完成、待处理和失败数量，失败保留原因与重试入口；不阻塞应用启动。

**补齐未完成时只能对已有指纹的图片准确判重。** 新上传仍立即计算指纹，但与尚未扫描旧图的重复不能保证发现。上传页应在这段时间显示简短覆盖状态；不能把未覆盖解释成“没有重复”。

显式替换走现有流程：新原图计算自己的指纹，发布成功后随当前原图引用一起切换；失败继续使用旧原图及其指纹。旧图替换为新内容后，再上传旧内容不应命中已退役的原图。首版不改变显式替换是否允许使用别的图片内容。

持久指纹随完整数据库备份保留；上传会话在备份归整时会清除，不能只依赖会话字段。恢复继续遵守当前同版本、同数据库结构要求，不增加跨版本备份兼容机制。指纹补齐任务须纳入现有备份暂停与恢复归整边界。

### 4.6 公开 API 与 PicGo

普通上传的 Web、公开 API 与 PicGo 使用同一原文件判重标准。API / PicGo 的重复处理方向已确认：明确报错，不自动返回已有图片链接。

公开上传 Token 只有上传权限，不能借“查重”取得已有私有图片的详情或地址。建议重复返回 `409 / UPLOAD_DUPLICATE`，`stage = deduplication`、`status = not_created`、`imageId = null`，提示登录图库核对。不向该 Token 返回旧图名称、ID、私有链接，也不改变已有图片权限。

Web 已登录所有者的上传响应可使用独立 `existingImageId` 跳转详情。该字段不冒充本次创建的 `imageId`。

PicGo 当前会将非 201 响应作为失败并中止本次输出。按已确认行为，需要补充明确的“已存在、未新增”提示与实际批量行为验收，并更新 OpenAPI、调用示例和测试。重复结果不提供可继续插入编辑器的旧图链接。上述错误字段与响应结构仍是本稿的接口设计建议。

## 5. 交付顺序与验收重点

本轮已授权更新方案与设计独立前端原型。原型计划复用现有 AdminShell、HeroUI 与 Tailwind，展示集合创建、修改、删除，三个模板的筛选结果，以及 Web 重复跳过和 API `409` 错误反馈。数据与状态变化仅在原型内模拟，不接入真实上传、指纹计算、业务接口或数据库。

以下是候选产品交付单元，不是已授权的业务实施任务清单。已确认选择见第 1 节，其余建议随原型继续评审；原型运行与界面检查结果另行记录，不能代替产品功能验收。

| 顺序 | 可独立验收的交付         | 关键结果                                                                              |
| ---- | ------------------------ | ------------------------------------------------------------------------------------- |
| 1    | 智能集合完整使用流程     | 三个模板可保存、打开、修改和删除；复用图库查看与批量操作；实际数据变化后正确匹配      |
| 2    | Web 完全重复检测         | Local/S3 上传、同批和跨标签页并发最多新增一张；重复项可查看已有图片；候选文件正确清理 |
| 3    | 旧图库补齐与图片生命周期 | 补齐状态真实；回收、恢复、永久删除、替换、备份恢复后指纹仍指向正确的当前原图          |
| 4    | API / PicGo 合约闭合     | 所有入口遵守已确认的重复处理规则；错误信息、权限、插件和 OpenAPI 一致                 |

第一项可先交付。重复检测整体完成以 2–4 的适用范围均通过为准，不能用“新 Web 上传可判重”代表旧库和其他入口已覆盖。

**智能集合验收：** 无标签进入/退出；标签改名与删除；7 天边界前后 1 毫秒；10 MB 边界前后 1 字节；替换成功/失败；回收与恢复；列表/总数/邻居一致；翻页时相对时间不漂移；新进入图片不加入旧选集；批量加标签后正确退出；后台完成通知不清空有效选择；另一窗口删除标签后出现刷新提示，刷新后归属或失效状态正确；打开/刷新不被无限期旧缓存覆盖。

**重复检测验收：** 改名同文件、同名不同文件、修改 EXIF、同批重复、Web/API 并发、S3 直传/中转、上传取消、数据库提交失败、重复候选清理失败与重启、处理中/失败/私有/回收状态、存量多重命中、存储停用、补齐中断、替换后旧内容重传、恢复后的再次上传。断言图片数、处理任务数、文件占用及已有图元数据，而不只检查 Toast。

**界面验收：** 复用 HeroUI、现有条件条、上传结果组件与图库详情；新增图标来自 Lucide 或 Gravity UI，布局使用 Tailwind。按现行约定覆盖桌面/手机、浅深色、短视口、键盘焦点和加载/空/错误/成功状态。设计对照与业务功能分别记录。
