## 4. 任务与依赖规则

任务分为规格、设计、实现和验收。每项只有一个明确的主要交付结果，默认按一个可独立评审的 PR 拆分。每项实施任务的必填信息见[任务模板](./todo.md#实施任务模板)。

| 状态                 | 判定条件                                                                           |
| -------------------- | ---------------------------------------------------------------------------------- |
| Draft                | 需求、规格、设计或验收尚未明确，不能实施                                           |
| Blocked              | 任务已明确，但必需前置未完成；可做独立调研，不实施依赖尚未交付内容的工作           |
| Ready                | 全部直接前置为 Done，所需规格及设计已评审，验证方法可执行                          |
| In progress / Review | 实施中或待评审；代码存在、PR 已开不等于完成                                        |
| Done                 | 全部前置仍为 Done；交付已合并或文档/设计已验收；自身验收与相关检查通过；证据可追溯 |

后置任务不能绕过未完成前置。Issue 关闭须核对完成原因和证据；取消或重复关闭不能满足依赖。前置重新打开、契约变更影响下游时，重新检查下游的依赖与验收。

本地只维护任务定义、直接依赖和链接；反向关系从同一份依赖计算。P2-TASKS 检查缺失 ID、自依赖、循环和需求遗漏。共享迁移、锁文件及接口改动按实际边界协调，不把所有模块互设双向依赖。

已同步的 M1/M2 任务以 GitHub 作为执行状态来源，原生 blocked by / blocking 关系已逐项回读核对。本地 `node docs/tasks/check.mjs` 已检查定义完整性及依赖无环；目前尚无 GitHub 自动拦截，P2-DEPENDENCIES 需交付检查并核实实际启用的合并规则。在此之前按人工检查执行，不能声称 GitHub 已自动阻止后置完成。

前后端分开时先交付接口约定。模拟数据任务只能验收界面本身；用户可用功能必须依赖真实接口和界面集成。无需界面的后端任务写明原因，不把不相关设计作为前置。

## 5. Figma 与前端任务

以[设计索引](../design/README.md)定位具体节点，不能只链接整个 Figma 文件或使用 UI-* 语义键解锁开发。每项界面任务写明页面入口/路由、桌面/手机/状态节点、实际组件、响应式规则、权限和数据来源；路由以规格确认值为准。

前端必须遵循[HeroUI 组件复用规则](../design/handoff.md#heroui-组件复用规则)：通用控件优先使用现成组件，复杂业务通过组合或有明确理由的专门组件实现。保留原型的布局和已确认流程，通用控件细节按 HeroUI 统一，不为此批量重画原型；组件映射、自定义理由和必要差异写入任务模板并在评审中核对。

桌面和手机在同一功能任务验收，或建立有明确依赖的适配任务。缺少手机验收不能标为完整交付。DES-01–07 及 DES-06 各子范围仅阻塞对应界面；代表图已补的项目继续完成适用规则与真实交互验证，不重复恢复过时的补图安排。

PRD 定义行为，Figma 定义已确认视觉与交互。示例数字、预填值、演示分页和旧展示项不能自动变成产品要求；冲突须明确记录并按批准的规格处理。相册手动排序已取消，固定展示规则和封面继续实现，图库查询排序保留。

## 6. 验证与完成

按改动执行适用的测试、类型、lint、格式和构建，记录实际命令及结果。现有完整检查入口如下；这是一份执行要求，不是本轮已经运行的报告：

```sh
pnpm run format:check
pnpm run lint
pnpm run typecheck
pnpm run test:unit
pnpm run build
pnpm run test:integration
pnpm run test:browser
```

业务任务新增必要的真实测试和浏览器断言，注明由本任务提供的测试文件与命令，不使用无测试的成功占位。Docker 双架构由 GitHub Actions 验证；Ego 未覆盖的浏览器另记环境和结果，单浏览器报告不代表四浏览器兼容性通过。

准备阶段完成需满足：全量需求无遗漏、十份已评审规格、完整实施任务及直接依赖、具体设计节点或明确设计前置、可执行验收方法，以及已验证的依赖检查与合并约束。材料可分批细化，不必等待不相关模块才能开展已具备条件的任务。

第二阶段完成以 PRD 全部要求和 26.1–26.13 实际证据为准，不以 Issue 数量或原型数量判断。实际 GHCR 发布尚未执行，必须单独记录；历史 runtime 的测试数量不视为本阶段运行结果。
