## 1. 目标与边界

所有者可以用相册和标签组织图片；同一图片加入多个相册，文件只保留一份。相册独立保存加入时间。删除相册或标签只移除组织关系，不删除图片。回收保留关系，恢复不重建已删除的相册或标签。

collections 负责相册、标签、成员关系、固定展示规则和封面身份。upload 负责队列与接收流程，library 负责图片查询和批量操作页面，sharing 负责分享设置、授权与访客展示，media 负责图片生命周期。没有文件夹、嵌套相册、标签颜色配置、公开相册管理 API、文件复制或额外封面上传。

参考 [Google Photos 相册说明](https://support.google.com/photos/answer/6128849?hl=en)：相册移除与图库删除分开，封面属于相册。这里只采用组织关系模式，Ariso 的权限、回收和分享仍以 PRD 为准。

## 2. 当前工程与采用方式

T-COL-01 已沿用 Drizzle、better-sqlite3 和 Zod 建立相册、标签及关联表，使用当前数据库连接及迁移目录。runtime 已开启 SQLite 外键；关系清理使用 [SQLite 的 CASCADE/SET NULL](https://www.sqlite.org/foreignkeys.html)，不用后台扫描弥补悬空关系。

标签大小写匹配使用 Unicode 默认完整大小写折叠，并统一 NFC 规范化；例如 `Go/go/GO` 对应同一个键。依据 [Unicode 大小写说明](https://www.unicode.org/faq/casemap_charprop.html)，实现时选用经核对的成熟实现，不自己维护映射表。[SQLite NOCASE](https://www.sqlite.org/datatype3.html#collating_sequences)只处理 ASCII 大小写，不能独自满足此规则。名称键唯一约束仍由数据库保证。

## 3. 数据模型与输入

以下为逻辑结构，实际迁移引用 media 的真实表和字段，不另建图片副本。

| 表             | 必需字段与约束                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `albums`       | ID、name、description、可空 preferred_cover_image_id、created_at、updated_at；名称不唯一；封面指向图片，永久删除图片时 SET NULL |
| `album_images` | album_id + image_id 联合主键、joined_at；两个外键删除均 CASCADE；加入时间属于关联，不属于图片                                   |
| `tags`         | ID、display_name、normalized_key 唯一、created_at、updated_at                                                                   |
| `image_tags`   | image_id + tag_id 联合主键；两个外键删除均 CASCADE                                                                              |

ID 使用项目统一的不透明 ID 方式，删除后重建得到新 ID。时间存 UTC。只有一个所有者，不添加多租户字段或权限继承结构。索引至少覆盖相册的加入时间及图片反查关系、标签查图片；所有排序都有图片 ID 作为固定次级排序。具体查询计划在十万图片样本中验证。

已确认输入规则：相册名称 1–100 个 Unicode 码点，标签名称 1–50 个，描述最多 2000 个；统一去除首尾空白和 NFC 规范化。名称不允许换行和控制字符；描述允许换行。空名称拒绝，描述为空保存为空字符串，均按纯文本展示。不同相册可同名；选择器同时展示封面、数量和短 ID 以区分，不擅自加编号改名。

标签键由规范化名称完整大小写折叠后再 NFC 得到，不合并内部分隔空白，不使用 NFKC 将全角字符等一并折叠。创建/匹配已有键返回原记录，保留首次成功创建时的显示形式。并发创建由唯一键竞争后读取胜出记录，不能产生两个标签或改写原显示名称。

标签重命名为未占用的名称时保留 ID 和图片关系；撞到另一个标签则报冲突，不自动合并。仅改变大小写、规范化后仍是原键时视为无变化，保留首次显示形式。相册重命名不受同名限制。

## 4. 图片关联与上传交接

### 4.1 普通关联操作

添加关系只接受存在且未回收、未开始永久删除的图片；pending、processing、failed、private 或存储停用不阻止元数据管理。移入回收站后不能从普通页面新增或修改其关联，既有关系保持；删除整个相册或标签仍会清除其中隐藏的关系。

重复加入同一相册或重复添加标签是无变化成功，不刷新 joined_at、不改变顺序。明确移出相册后再加入，会生成新的加入时间，按固定展示规则重新定位。移出操作不删除图片，也不影响其他相册。批量操作由 library 根据用户显式选择的 ID 调用，包含同一查询跨页保留的选择；当前页全选只增加当前页，不能扩张成所有搜索结果。

批量加入多个相册/标签时，每张图片一次短事务；任一目标不存在则该图整项失败，其他图片可以成功。返回逐图结果，区分新增、已存在和错误；不能把部分失败显示成全部成功。

### 4.2 上传批次与 API

Web 整批统一设置；API 单文件请求支持一个或多个 albumId，不能以相册名称代替 ID。API 按标签名称匹配或创建。上传页快速创建只输入名称，高级设置留在管理页。

建议在正式提交批次/请求时，先验证全部相册 ID，并在同一短事务中匹配或创建标签，固定目标 ID。一个批次的所有文件使用同一组 ID。显式快速创建和 API 自动创建的标签一旦成功便保留；之后传输取消或失败也不自动删除空记录，以免删除已被其他操作使用的标签。

`upload` 接收原文件后，在 media 接收资产和对象责任交接的**同一个同步数据库事务**中调用 `attachAcceptedImage(tx, imageId, selection)`。重新检查固定的相册/标签 ID，插入关系并保存加入时间；事务内不进行文件 I/O、网络调用或 await。

如果上传期间目标被删除，返回 `COLLECTION_TARGET_REMOVED`，该文件的整个接收事务回滚。不能静默少加一个标签、按同名新记录替换或自动重建。尚未交接的原文件继续由 upload 负责失败反馈与清理，不能产生无责任方的对象；upload 规格必须落实这条失败路径。已经交接成功的其他文件不回滚。重试前重新选择当前目标，生成新的提交快照。

多张文件按各自接收事务保存加入时间，不承诺并发传输后仍按浏览器选文件顺序排列。处理完成先后不再改变顺序。媒体处理之后失败仍保留已提交的关联，供所有者查看和重试。

## 5. 固定展示规则

相册内容固定按 `joined_at` 降序、`imageId` 升序展示。加入时间属于相册与图片的关系，与图片上传时间分开；每个相册独立保存加入时间。搜索或筛选只读取这一顺序的子集，不改变全相册规则。

相册内容遵守图库默认 40、可选 20/40/80 的分页或加载更多规则；library 负责通用查询和 URL 状态。自动封面与分享页使用同一固定规则，并在分页前按各自资格条件过滤。

回收不修改加入时间；恢复后按保留的加入时间重新参与展示。明确移出后再次加入会生成新的加入时间。并发接收以实际保存的加入时间为准，同值使用图片 ID 确定顺序；图片处理完成先后不改变展示规则。

## 6. 封面选择与呈现

手动封面必须是该相册中未回收、未开始永久删除的公开图片。未指定时，按第 5 节固定展示规则从**全相册**取第一张公开且未回收、未永久删除的图片，不能只检查当前页面。私有图永不作为相册封面，即使所有者能看原图。

手动封面改私有或移入回收站时，保留选择 ID，但展示暂时回退到自动封面；它恢复公开和正常库状态后，自动恢复手动封面。明确从相册移出会清空选择；再次加入不会自动重设。永久删除通过外键清空选择。所有者可以主动切回“自动封面”。

本草案严格按 PRD 的“第一张公开图片”选择身份：如果选中的图片仍在处理、处理失败或存储停用，展示对应占位，**不继续向后换另一张公开图**。正常时使用现有 thumbnail，没有封面副本，不改用原图/默认外链，不自动重处理。

封面在处理未成功时统一占位；所有者从图片详情仍可按 delivery 规则读取失败图已保存的版本，这不是封面例外。其余封面内容由页面组合层通过 delivery 判断当前用户能否读取，匿名不能绕过状态要求。候选文件不可作为成功缩略图。底层文件丢失显示加载错误，不偷偷换版本。无公开成员时使用通用占位。

分享页不得用封面身份绕过公开访问条件；分享内容和封面展示字段由 sharing 再裁剪。查询返回的身份只是候选，不是访问授权，不持久保存 S3 临时 URL，也不需要 collections 直接调用 storage。

## 7. 删除、回收恢复与分享

删除相册是立即执行的短数据库事务：删除相册、全部成员关系和封面设置。相册不进入回收站，不删除图片、版本、文件或媒体处理任务。取消分享与删除相册是不同操作，提示必须准确。

sharing 建表时以 albumId 外键 CASCADE 清除该相册的分享记录及授权依赖。每次授权仍检查实际分享和相册是否存在；已发 Cookie 不能脱离现存记录放行。删除后不能继续获得分享内容，但不能撤回访客已经下载的文件；已有 S3 签名剩余有效期仍遵循 delivery。公开图片独立外链继续按图片自身状态工作。

删除标签同样立即清除标签与所有图片关系，包括回收站图片；不删除图片，不合并其他标签。同名新建是新 ID，不能继承旧关系。

media 回收图片只改生命周期状态，不删除这四张表中的关系；恢复后显示仍存在的相册和标签，并沿用原加入时间。若相册或标签已经删除，不补建。永久删除开始后关系可暂留供清理诊断，但查询排除；对象全部清理成功、最终删除图片记录时，由外键清理关系和封面。

存储停用不妨碍相册/标签重命名、成员移除和删除；文件读取仍失败。没有为元数据操作增加存储探测或文件写入。

## 8. 查询、接口与错误

管理页面提议为 `/albums`、`/albums/{albumId}`、`/tags`；标签查看图片进入 library 的标签 ID 筛选。管理入口均要求 identity 所有者 Cookie；管理写入同时复用 identity 已批准的来源/CSRF 检查；上传 Token 只能通过 upload 调用既定关联能力，不能直接调用这些管理接口。

| 内部能力                                                        | 契约                                                                                                                                                                   |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `listAlbums / listTags`                                         | 分页和名称搜索；所有者数量仅统计未回收、未永久删除的成员，包含 private/failed/存储停用；不复用为匿名数量                                                               |
| `createAlbum / updateAlbum / deleteAlbum`                       | 名称、描述、手动封面分别按上述规则变更；delete 不调用 media 文件删除                                                                                                   |
| `getOrCreateTags / renameTag / deleteTag`                       | 唯一名称键匹配、保持 ID、冲突明确；供 Web 与 API 共用规范化规则                                                                                                        |
| `prepareUploadSelection(tx, input)`                             | 完整验证目标并解析/创建标签，返回固定 IDs；错误回滚准备事务                                                                                                            |
| `attachAcceptedImage(tx, imageId, selection)`                   | 必须加入调用者的 media 接收事务，不独立提交；检查目标仍存在                                                                                                            |
| `addMemberships / removeMemberships`                            | 单图事务、多图逐项结果；重复操作无变化成功；不以标签名称重新绑定旧请求                                                                                                 |
| `resolveAlbumCover`                                             | 返回选中的图片身份、手动/自动/空状态；内容授权留给 delivery 组合层                                                                                                     |
| `readAlbumMembers / readAlbumNeighbors / readAlbumMemberStates` | 同一 tx 内按固定展示规则分页、取前后邻居或最多 80 个明确 ID 的状态；调用者明确 normal/public 范围，public 排除私有/回收/删除中，在分页和计数前过滤；不作文件读取或授权 |

补充 `countAlbums(tx)` 供当前用量读取，计算现存相册行数，包含空相册，不因多个成员关联重复计数；不读取文件或向 analytics 反向回调。

成员只读接口供 library/sharing 组合：normal 包含所有者正常库各状态，public 是匿名候选集合而不是最终内容授权；返回内部记录，由调用者按访问上下文裁剪。邻居和游标始终复用本规格的排序/次级 ID 规则；匿名游标不承载隐藏名称或上传时间，由分享层以有效公开锚点在服务端解析。sharing 的前后邻居按其已批准精简大图契约接入，不因此新增公开管理 API。

列表默认每页 40，可选 20/40/80；相册/标签列表按创建时间降序、ID 升序稳定排序。名称搜索按规范化后的文字子串，不把 `%`、`_` 当用户通配符。只查本页和所需聚合，不能每张卡片单独查询全部关系或读文件。数量直接查询关系与图片状态，不引入容易失步的缓存计数列。

Web 管理接口使用项目的结构化错误格式，区分无会话 401、输入非法 400、目标不存在 404、重命名冲突或上传目标失效 409、数据库故障 500。仅重复删除已经不存在的相册/标签可作无变化成功，不能吞掉真实数据库错误。批量响应保留逐图错误码和原因。

日志记录操作、对象 ID、结果和错误上下文，不记录 Cookie 或上传 Token。不为普通关系管理新增审计系统、后台队列或事件总线。

## 9. 代码边界与实施顺序

预计新增 `src/server/collections/` 的 schema、repository、service、validation 和公开入口；迁移放到现有迁移目录。实际文件按职责拆分，不机械生成无实现的空层。页面与交互放到 `src/app/` 对应路由及组件目录；认证、delivery、library 的组合留在入口，不从 collections 导入页面代码。

TypeScript 严格类型、camelCase 函数、数据库 snake_case，沿用 Prettier/ESLint。示意调用只强调事务归属，具体 media 签名按其实现落地：

```ts
db.transaction((tx) => {
  const image = acceptImage(tx, acceptedInput);
  attachAcceptedImage(tx, image.id, selection);
  completeUploadHandoff(tx, uploadId, image.id);
});
```

始终遵守真实 ID、外键、同步短事务和逐项结果。要改变封面选择、名称匹配、上传失效处理或回收恢复语义，先修订规格并评审。禁止文件复制、按同名补建已删除目标、用空分享回调冒充删除分享已验收。

先交付 `COLLECTIONS-BASE` 的模型与关系，再交付 `COLLECTIONS-COVER` 的封面和管理界面。upload、library、sharing 分别完成真实集成；删除分享的完整验收须等 sharing 接入。前端还依赖身份认证和已评审设计，不能仅凭后端表已创建宣布功能完成。

## 12. 本轮评审场景

用户于 2026-09-17 确认以下五组建议；PRD 已规定的删除不删图、多相册、标签不区分大小写等仍保持。

1. **固定展示与恢复（按最新决定修订）。** 最新加入的图片在前，加入时间相同用图片 ID 升序。把 B 放回收站只隐藏 B；恢复时沿用原加入时间。明确移出再加入产生新时间。
2. **封面临时失效。** 手动选 A；A 改私有或回收，暂用第一张公开图 B；A 恢复公开且正常后，又显示 A。若明确从相册移出 A，之后重新加入不会抢回封面。选中的公开图正在处理或存储停用时显示占位，不自动换到 C。
3. **上传中删目标。** 十张图统一加入“旅行”和 Go。前四张已经接收，随后删除 Go；前四张照片保留且 Go 关系随删除移除，剩余尚未交接的文件报目标已删除。重新选择后再提交；不会悄悄去掉 Go 并报全部成功，也不会自动绑定新建的同名 Go。
4. **空记录与命名。** 上传页创建“旅行”，或 API 自动创建 Go，后来上传取消/失败，空相册/标签保留供手动删除。Go 已存在时输入 go 复用且显示 Go；把另一个标签改成 GO 会报重名，单独把 Go 改成 go 则不改变显示形式。名称/标签/描述上限分别为 100/50/2000 字符。
5. **删除与恢复。** 相片同时属于“旅行”“精选”和 Go，放进回收站后删除“旅行”和 Go，再恢复只回到“精选”。“旅行”的分享立即失效；照片自身公开外链仍按图片状态恢复可用。重新创建同名相册/标签不会恢复旧关系。

本规格及其余九份业务规格均已完成产品评审；代表原型已集中补充，当前按设计交接细化实施任务。设计记录不代替真实关联、上传交接和恢复流程的验收。
