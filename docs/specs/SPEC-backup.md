## 1. 已确认的范围

目标用户是站点所有者。即使原服务器和原 S3 都不可用，也能凭备份，在空白的新 Ariso 实例中恢复完整站点。

| 决定       | 已确认行为                                                            |
| ---------- | --------------------------------------------------------------------- |
| 备份范围   | 整站备份，包含本地和 S3 的实际图片文件                                |
| 执行方式   | 仅手动创建；第一版不做定时自动备份                                    |
| 备份期间   | 暂停修改，保留浏览和外链访问                                          |
| 结束处理   | 备份完成或失败后恢复修改操作                                          |
| 恢复目标   | 只恢复到空白的新实例，不覆盖已有站点                                  |
| 存储归属   | 保留原存储划分；本地图片恢复到新机器，S3 图片恢复到指定的新 S3        |
| 新 S3 配置 | 恢复时填写新的位置和凭据，不依赖原 S3 可访问                          |
| 当前阶段   | Local/S3 代码已接入，真实提供方、浏览器与最终复核进行中；暂不发布部署 |

不包含部分图片合并恢复、已有站点覆盖、跨存储类型迁移、增量备份、定时任务或数据库降级。上述能力不在第一版范围内。

### 当前实施片段

已实现本地与 S3 创建、下载、取消、删除，以及空白新实例的授权、分块接收、解密、多目标配置与测试、恢复准备和重启启用。停用的 S3 也按持久引用读取实际文件；任何必需远端文件无法读取时整次备份失败，不跳过后生成不完整包。S3 实际提供方和浏览器证据尚在运行，最终结果以 [S3 实施记录](../verification/backup-implementation/s3.md) 为准。

本轮采用 ZIP64＋标准 age 密码加密；恢复要求构建版本、完整提交修订与数据库迁移版本一致。无显式构建身份时不开放创建备份或恢复任务。ready 表示数据已准备完成，仍须部署者手动重启；浏览器不会直接覆盖正在运行的数据库。

## 2. 当前实现与方案依据

| 已核实事实                                                                                                                                 | 对方案的影响                                                            |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| [升级指南](../guides/upgrading.md)目前采用停机后归档数据目录，并保存部署配置                                                               | 这是现有运维方法，不能直接满足保留浏览的产品备份                        |
| [运行数据库](../../src/server/runtime/db.ts)启用 SQLite WAL                                                                                | 不能只复制运行中的数据库主文件；复用已安装 better-sqlite3 的 `backup()` |
| [S3 适配器](../../src/server/storage/s3.ts)按存储 ID 划分对象位置                                                                          | 本机目录归档不含 S3 图片；恢复要保留逻辑 ID，替换实际存储位置           |
| [存储维护](../../src/server/storage/maintenance.ts)启动后扫描全部存储；[扫描](../../src/server/storage/scans.ts)会清理没有数据库引用的对象 | 恢复未完成前不能启用恢复库及其清理任务；停用存储并不能阻止维护清理      |
| [媒体队列](../../src/server/media/queue.ts)同时承接持久任务和临时预览                                                                      | 保留浏览需要继续执行 TIFF 等临时预览，不能简单停止整个队列              |
| [初始化](../../src/server/identity/setup.ts)已有初始化码授权                                                                               | 恢复复用该授权，不在空实例开放匿名文件导入入口                          |
| [启动预检](../../src/server/startup/preflight.ts)会建库、迁移和准备初始记录                                                                | “空白实例”指未初始化且没有用户业务数据，不等于数据库文件不存在          |
| [现有图库 ZIP](../../src/server/delivery/archive.ts)是有选择范围和版本限制的下载功能                                                       | 可复用流式归档和存储读取能力，不能直接复用其备份语义                    |

[Immich](https://docs.immich.app/administration/backup-and-restore/)和[PhotoPrism](https://docs.photoprism.app/user-guide/backups/)都区分数据库与媒体文件。Ariso 依照本次已确认范围，将两者纳入同一份可恢复交付物。

[SQLite Online Backup API](https://www.sqlite.org/backup.html)支持数据库一致副本；[better-sqlite3 文档](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise)说明备份期间可以继续使用连接。该能力不自动解决图片替换、删除与文件复制的一致性，需要以下内容修改暂停机制配合。

## 3. 用户流程

### 3.1 创建与保存

设置中新增“备份与恢复”入口。已有站点提供创建、查看进度、下载和删除备份；恢复说明指向新实例的初始化入口。

1. 所有者查看备份范围、各存储文件量和本机所需空间估算，并设置独立备份密码。说明暂停修改会持续到备份结束，不承诺固定耗时。
2. 手动开始；服务端先暂停新的内容修改，等待已进入执行阶段的相关写入结算。
3. 创建数据库副本，并从各存储流式读取需要保留的对象，生成单个备份文件。
4. 文件完整写入且必要校验通过后才显示“备份已生成”，恢复修改操作。
5. 所有者下载备份到自己控制的位置。下载断开不销毁服务器上的已完成文件，可以重新下载。

**先在服务器生成完整文件，再由所有者下载保存。** 备份任务不绑定浏览器长连接；刷新或关闭页面不会取消任务，也不会延长修改暂停到下载结束。暂不增加“直接把备份包发送到远端 S3”的目的地管理。

生成目录与图库对象目录分离。备份文件不进入公开静态目录、不被本轮或后续备份递归打包；查看和下载均要求所有者权限。显示文件大小、创建/完成时间、状态与失败原因，允许手动删除已完成备份。第一版不自动删除历史备份。

“服务器上已生成”和“用户已保存到另一处”分别表达。HTTP 下载完成不能证明用户在原服务器损坏后仍能取得该文件，不显示未经证实的异地保存状态。

### 3.2 在新实例恢复

1. 部署空白的新实例，在初始化页选择“从备份恢复”，使用当前初始化码授权。
2. 提交备份文件并输入备份密码。读取版本、备份时间、图片数量和存储列表。
3. 确认恢复后的站点公开地址。逐个填写新 S3 的 endpoint、bucket、目录前缀及凭据；本地存储保留原划分，使用新实例数据目录。
4. 验证目标位置与连接，展示所需空间和对象数量。S3 使用该次恢复独占的新命名空间；可以在已有 bucket 中使用新前缀，不要求整个 bucket 为空。
5. 在暂存数据库和暂存目录中恢复数据，将远端图片写入新 S3；正常实例仍不启用恢复库。
6. 全部内容和配置检查完成后，显示“数据恢复完成，等待启用”，提示部署者重启一次。
7. 重启时，在正常预检和后台任务启动之前完成恢复启用；随后使用备份中的所有者账号登录。

新 S3 的连接结果必须来自当前配置 revision 的实际验证，全部目标的 testedRevision 与 revision 一致且测试通过后才可执行，不能继承旧地址的“测试通过”。原存储 ID 保留，新位置为指定前缀下的 `ariso/<原 storageId>/`。旧 CORS 检测结果失效，即使站点域名没有改变也一样；重新验证前沿用现有服务器中转上传行为。保留原存储的默认归属和启用/停用意图，不在恢复时自动启用原本停用的存储。

旧站数据库、原本地文件和原 S3 不作为恢复数据源，也不因新实例恢复而被修改。图片、相册、标签、对象及分享的逻辑身份保留；存储位置和配置改变，不重新上传为一批新图片。

已存在所有者或用户业务数据的实例拒绝恢复。正常初始化与恢复不能并发完成，避免同一实例出现两个互相覆盖的初始化结果。

## 4. 备份内容

| 内容         | 备份规则                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------- |
| 数据库       | 账号、图片和版本、相册、标签、关系、分享、设置、统计、可恢复持久任务                           |
| 图片文件     | 所有已保存的原图、压缩图、缩略图、水印图、尺寸版本，包含回收站图片；停用存储中的文件仍在范围内 |
| 持久任务依赖 | 已接收但未完成的媒体任务、替换候选、尺寸任务实际引用的已保存对象及处理参数                     |
| 站点素材     | Logo、Favicon、水印及持久任务引用的素材                                                        |
| 解密材料     | 恢复已有加密业务配置所必需的材料；具体保护方式见第 7 节                                        |
| 说明与清单   | 格式版本、实际应用发布版本/修订信息、数据库迁移版本、快照时间、各存储及文件清单                |

包内对象按存储身份和对象 Key 记录，不依赖原机器的绝对路径。归档封装已采用 ZIP64 外包标准 age v1 密码加密，参数与实际验证见[技术方案](../../tasks/plan.md#3-备份格式与加密)。第一版只承诺已定义格式的读取，不预设兼容未来格式。

不打包程序、依赖、容器镜像、日志、已有备份、临时预览和未完成的浏览器上传。新实例按正常安装方式准备运行环境。恢复页面保留可诊断的版本信息，不用当前仍为开发值的 `package.json` 版本冒充实际发布版本。

临时记录需要在备份副本或恢复副本中归整：旧浏览器上传、探测和预览不自动续跑，原机器的 `temporaryPath` 不能进入新实例文件清理。已经持久接收的媒体任务保留；当前[处理逻辑](../../src/server/media/process.ts)可以在临时输入不存在时从正式原图或替换候选重新读取，不必逐个迁移临时绝对路径。

对象清单以数据库中的持久引用为准，不直接打包整个 S3 bucket。已确认删除的内容和无引用垃圾不属于备份；待清理对象允许已经不存在。仍被保存版本或可恢复任务需要的文件若读取失败，则整次备份失败，不能跳过后声称完整。

## 5. 暂停修改与一致性

暂停的是站点内容修改，不是所有数据库写入。登录、会话续期、浏览所需临时预览及访问统计仍需工作；备份中的统计以数据库副本捕获到的数据为准，不包含之后的访问。

暂停范围包含后台和 HTTP 两侧：新上传及上传完成交接、图片替换、永久删除、回收操作、相册标签修改、分享修改、配置修改、持久媒体处理、素材及存储对象清理。对公开上传 API 同样生效，不能只禁用页面按钮。

准备阶段分两步：先禁止新内容修改，媒体队列继续完成已受理前台请求依赖的处理；这些请求结算后，再暂停后台领取新的持久任务和发起清理，并等待当前批次结束。队列中的待处理、待重试和失败任务不要求全部清零。等待有明确上限；无法进入稳定状态时，本次备份失败并恢复操作，不强行终止正常任务来换取备份成功。

正在处理的公开 API 上传还可能等待派生结果，因此第一阶段保留媒体队列执行，直到该请求结算或备份准备超时。不会等待所有 HTTP 连接结束，浏览和外链始终保留；也不修改现有上传等待期限。具体 gate、后台 pause/resume 和超时验证见技术方案。

已发出的 S3 直传签名不能撤回，但只允许写入上传或探测临时对象。暂停新签名和正式交接，等待已经开始的交接完成；按持久引用复制对象，不靠等待签名过期推断远端不会再写。迟到的临时对象继续由原站已有清理机制处理。

数据库副本生成后，只从该副本读取备份清单，避免混用实时查询。持久文件和配置保持冻结，直到归档完成或失败。复用 `backup()`，不复制 live 数据库主文件，也不在覆盖整个文件传输的长数据库事务中等待网络。

备份任务成功、失败或取消均在退出路径恢复调度和修改入口。进程退出时备份任务终止，正常重启将未完成备份记录为中断并解除暂停，不因旧状态文件一直阻止用户操作；尚未真正退出的复制任务必须先停止，不能一边继续制作旧备份一边解除暂停。

## 6. 恢复的启用与失败处理

恢复只写新实例的暂存空间和明确指定的新 S3 命名空间。恢复库在启用之前不开启普通上传、媒体、探测或孤儿扫描。不能只依靠 `storage.enabled=false` 隔离恢复。

复用当前初始化授权，在文件完整、数据库及关系检查通过、新配置可解密后准备启用。下一次启动先只准备数据根目录，在正常业务目录初始化及正式开库之前完成恢复启用：放置本地素材及对象、移出旧数据库和 WAL、最后发布恢复数据库。文件与相关目录同步后才持久化完成记录。未完成时继续同一次启用或返回明确错误，不让半成品进入正常后台清理。

首版由用户重启以完成启用。当前 Compose 示例没有自动重启策略，不把“退出应用”当作“应用已自动重新启动”，也不为此引入额外进程管理器。

| 情况                             | 对用户可见的结果                                                    |
| -------------------------------- | ------------------------------------------------------------------- |
| 源文件读取失败、备份空间不足     | 备份失败、恢复修改操作，显示存储/文件和原因；不提供半成品为正式备份 |
| 浏览器关闭或刷新                 | 服务端任务继续；返回页面后可查询状态                                |
| 下载中断                         | 已完成备份保留，可重新下载                                          |
| 备份包损坏、密码错误或格式不支持 | 恢复不启用，给出对应原因；不以空站点假报恢复成功                    |
| 新 S3 写入失败或恢复空间不足     | 保持恢复未启用，保留明确结果和本次已写位置                          |
| 恢复中断                         | 不启用半成品；允许明确重试，重复执行不创建重复图片、不触碰其他对象  |
| 当前版本无法读取该数据库         | 在目标数据写入前拒绝，提示先安装匹配版本；不降级数据库              |

第一版要求先使用备份对应发布版本恢复，再按现有升级流程升级。数据恢复不等于 DNS、TLS、GitHub OAuth 回调或新 S3 CORS 已配置完成；完成页列出确实需要部署者处理的项目。

同一次恢复重试时，可以向该次独占的暂存目录和 S3 命名空间重新写入同一备份对象，不要求实现跨进程断点续传。换备份、换目标或放弃恢复时，明确展示旧暂存目录和远端已写位置及清理办法；不把旧半成品误认为新任务已经完成，也不通过扫描删除目标 bucket 的其他内容。

取消后仍有远端清理责任时，目标位置不可更换；允许只更新原坐标的凭据，再继续清理同一任务。完整 PUT 已发出但因取消、断线或服务错误没有确定结果时，空列表不能证明以后不会出现对象：保留待清理状态和初始化占用，显示 `RESTORE_REMOTE_WRITE_UNCERTAIN`，稍后重试发现并删除迟到对象后才解除。明确的 4xx 拒绝或未完整发出的请求可以结算；如果存储始终不给确定结果且对象也不出现，继续保留责任，需要检查对应命名空间和服务日志，不承诺取消总能立即完成。不能用固定等待时长或人工忽略确认替代结果。

旧图片和分享的路径身份保留。要让旧的完整 URL 继续可用，需要用户继续使用原域名并将其指向新实例；换域名不能由恢复程序自动修复外部文章中的旧 URL。已过期的分享仍按当前时间判断。整站回到备份状态也可能重新出现备份后已撤销的分享，恢复前需说明这一结果。

## 7. 密钥与账号处理

备份包含私有图片、密码哈希和恢复配置所需的解密材料。**整个备份包必须设置独立密码。** 密码不存放在包内；丢失密码无法解密。具体封装选用成熟可验证方案，不直接把现有小字符串加密函数当作大文件归档工具。

新实例保留其部署环境中的 `ARISO_ENCRYPTION_KEY` 和 `BETTER_AUTH_SECRET`，不要求用户编辑环境变量以恢复旧密钥。恢复时使用包内旧解密材料读取旧配置，再通过现有[配置加密函数](../../src/server/runtime/crypto.ts)用新实例密钥重新保存。

目前需要处理的业务字段是存储配置的两个凭据字段，以及 GitHub Client Secret、SMTP Password。新 S3 凭据按恢复表单替换。该变化在暂存数据库中完成，不修改原站配置，也不新增通用密钥轮换框架。

保留所有者密码、上传 Token 和分享记录；不延续浏览器登录会话及尚未消费的密码重置链接。恢复后重新登录，已有 PicGo 等客户端在地址和 Token 仍匹配时可继续使用。不得以恢复为由静默撤销全部上传 Token。

备份下载沿用所有者鉴权，恢复沿用初始化码。导入归档会跨越外部文件边界，必须限制解压到本次暂存目录、拒绝路径逃逸并处理磁盘不足；这是防止导入文件覆盖系统内容的实际边界，不引入签名服务或额外权限系统。

## 8. 模块责任与实现约定

仍维持单容器、SQLite 和现有 Web 进程，不要求 Redis、独立 Worker 或新数据库。

| 位置                                              | 建议责任                                             |
| ------------------------------------------------- | ---------------------------------------------------- |
| `src/server/backup/`                              | 备份清单、归档任务、进度、恢复暂存与启用协调         |
| 现有 `runtime`、`startup`                         | 数据库副本、生命周期，以及正常启动前的恢复启用       |
| 现有 `storage`、`media`、`upload`                 | 各自提供暂停/恢复和真实对象读写；保持既有模块所有权  |
| 现有 `identity`、`site`                           | 所有者与初始化授权、配置转换、公开地址及相关失效处理 |
| `src/app/settings/backup/`、现有 `/setup`         | 备份页面和恢复流程，复用公共外壳和现有组件           |
| `tests/unit/backup/`、`tests/integration/backup/` | 格式、错误和真实目录/数据库恢复测试                  |
| `e2e/` 与现有浏览器运行器                         | 备份期间使用、任务反馈、初始化恢复流程               |

以上是实施组织建议，不是已新增的目录或承诺的 API。正式接口与任务拆分在后续技术设计中确定，不为导出额外开放公共管理 API。

沿用 TypeScript、显式参数传入数据库/路径/配置、短同步数据库事务和异步文件 I/O。错误保留操作阶段、存储身份及对象位置；秘密不进入日志。已有 `better-sqlite3`、AWS SDK、`zip-stream` 优先复用；归档读取和密码封装能力需核对类型与官方资料后选型，本方案未新增依赖。

## 9. 验收与检查

实现验收必须使用新目录、新数据库和新的 S3 命名空间，不能连接生产数据做演练。

1. 混合本地、S3、多个存储、正常/私有/回收站图片，包含原图及各已保存版本，完成备份与独立恢复。
2. 在原服务器与原 S3 均不可访问的条件下，仅依靠备份、匹配应用版本和新目标配置完成恢复。
3. 对比恢复后的图片身份、文件内容、相册标签关系、存储归属、品牌素材及统计副本；验证实际登录、浏览、下载、分享和新上传。
4. 备份期间继续验证公开外链、私有权限、相册浏览及需要临时处理的 TIFF 预览；修改入口明确拒绝，HTTP/API 与页面行为一致。
5. 备份成功、失败、准备超时、取消及进程中断后都能恢复修改；不遗留一直暂停的站点。
6. 覆盖已在途上传、PicGo 等待结果、迟到 S3 PUT、图片替换、待重试任务和待清理对象；不遗漏任务必需原图，也不误报已删除对象缺失。
7. 损坏包、错误密码、缺失必需对象、新 S3 凭据错误、空间不足、恢复/启用中断都不能启用半成品。恢复重试不产生重复图片。
8. 原站和同 bucket 中其他命名空间保持不变。恢复启用前不执行恢复库的孤儿清理。
9. 空实例判断允许正常初始记录，拒绝已有业务数据；普通初始化与恢复互斥完成。
10. 验证新实例密钥下配置可解密、旧会话/重置链接政策、域名变化提示及版本不支持提示。

采用现有 Vitest 单元与集成框架；真实对象存储按[验证指南](../guides/verification.md)覆盖 Cloudflare R2 与 SeaweedFS。界面设计和桌面/移动端证据沿用[设计交付规范](../design/handoff.md)，产品方案确认不构成界面验收。

```sh

pnpm --dir integrations/picgo install --frozen-lockfile
pnpm run format:check
```

正式实现执行以下适用检查；实际完成情况见实施记录，不以文档核查替代：


始终保留错误和实际证据；不静默跳过必需文件、不降低断言、不把拟定验收项写成已通过。当前已授权正式实现、测试和本地隔离验证；生产发布部署仍不在本轮范围内。

## 10. 补充决定的确认记录

用户于 2026-10-22 明确确认以下五项，并要求先更新为已确认方案，再评估是否需要原型设计：

1. **备份保存方式**：服务器生成完整文件，所有者下载保存；第一版不自动发送备份到远端，也不自动清理历史备份。
2. **密码政策**：整个备份包必须设置独立密码；忘记密码无法恢复。
3. **恢复启用**：数据准备完成后由用户重启一次，不增加自动重启管理。
4. **账号与配置**：保留密码、上传 Token 和分享，重新登录；配置转为新实例密钥，恢复时确认公开地址。
5. **版本范围**：第一版先使用备份对应发布版本恢复，随后走正常升级流程。

上述实现细节已整理到技术方案：ZIP64＋age、独立工作线程、顺序分块上传、两阶段暂停、重启前发布及授权接口。Local/S3 代码均已接入，真实提供方、浏览器与最终复核状态以 [S3 实施记录](../verification/backup-implementation/s3.md) 为准；不能凭文档承诺任意大小、固定时长或跨进程断点续传。本轮不执行大文件或容量压测。

## 11. 原型设计评估

评估结论：建议先制作一套复用现有界面的局部交互原型。新增内容包含长时间任务、跨页面暂停修改反馈和初始化恢复，不仅是增加几个设置字段；需要通过实际点击验证用户能否理解当前状态及下一步，不需要探索多套视觉风格。

最小范围为两条流程和一个全局状态：

| 范围               | 原型需要验证的内容                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 设置中的备份流程   | 空态、独立密码、暂停修改确认、准备和复制进度、成功下载与删除、失败重试；区分“已生成”和下载/保存动作                                    |
| 初始化恢复流程     | 初始化码授权、选择备份并解密、摘要和版本检查、新 S3 位置/凭据及连接测试、恢复进度、失败纠错、等待重启、启用后登录；覆盖纯本地及多个 S3 |
| 备份期间的现有页面 | 继续浏览；上传、删除等不可用操作说明原因；可返回备份进度；任务结束后状态和操作恢复                                                     |

复用现有 AdminShell、设置分类、PublicShell、初始化表单和 S3 字段设计。恢复时需要输入新的存储位置，不直接继承现有存储编辑页“有图片引用时位置只读”的行为。桌面、手机、浅深色、短视口、键盘焦点和关键错误状态沿用项目规范；长 S3 配置使用独立流程页面，不挤入小确认框。

原型只使用模拟数据验证布局、状态和交互，不执行真实备份、上传私有文件或写入 S3。原型结果不能证明数据库一致性、加密正确性、暂停边界或断电恢复，这些仍由后端实验和集成测试验证。

用户于 2026-10-22 明确认可[隔离原型](../../prototypes/backup-restore/README.md)，当时要求先整理技术方案，暂不修改业务代码。该原型复用现有公共外壳、主题、设置分类和表单，覆盖创建备份、空实例恢复及暂停修改，作为正式前端依据。随后按用户授权完成 Figma 同步并开始本地业务实现；当前状态以本文开头与实施记录为准。
