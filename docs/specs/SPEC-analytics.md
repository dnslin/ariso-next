## 1. 目标与边界

所有者能看清当前有多少图片、相册，各存储中 Ariso 对象占用多少，以及公开图片的今日/累计访问、7/30/90 天趋势、热门图片和版本访问量。界面同时说明统计更新与不完整状态，不能把没有数据、尚未刷新和读取失败都显示成零。

analytics 拥有访问聚合、持久统计、每日保留及报表查询。delivery 决定是否计数和事件时点；media、collections、storage、upload 拥有当前资产、关系和对象记录。空间及数量读取提供方的数据，不另建一份容易失步的资产清单。

没有逐请求日志表、独立访客、IP/地区/设备/来源分析、下载独立指标、相册分享访问量、流量字节账单、配额或存储容量估算。不接第三方分析服务、Redis、消息队列或独立统计进程。全部统计接口仅供所有者，不是对外开放 API。

## 2. 工程依据

现有 runtime 使用单 Node 进程、better-sqlite3/Drizzle，SQLite 已开启 WAL、外键与 busy_timeout；`src/server/startup/server-start.ts` 通过进程内单例初始化。`src/instrumentation.ts` 排除构建阶段，因此统计定时任务只能接 Web 运行启动，不能在构建或迁移 CLI 中启动。

- [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html)可以在唯一键冲突时增量更新计数；[事务](https://www.sqlite.org/lang_transaction.html)用于保证同一批的每日、单图和累计计数一起提交或回滚。不要使用会删除再插入的 REPLACE 模拟加法。
- 报表标明日期范围与站点时区，采用成熟统计产品的通用表达；[Plausible 的时区说明](https://plausible.io/docs/general)以所选时区决定日界线。Ariso 的旧统计不重写仍按自身 PRD，不能借参考产品推导访客或来源指标。
- 图表使用项目技术栈内可用组件；现有依赖尚无业务图表组件。实施时先检查 HeroUI 及选定图表库的实际功能、体积、许可和键盘支持，再固定必要依赖，不在本稿虚构已验证版本。折线、组成条和排行榜需有文本/表格等价结果。

本轮是仓库与资料核对，不代表真实访问计数、关停恢复、图表或十万图片性能已经测试。

## 3. 唯一计数入口

入口组合仅消费 delivery 已批准的 `{ imageId, storageId, actualVersion, occurredAt }`，其中 occurredAt 是 UTC 事件时刻：本地首次返回文件字节，或 S3 成功签发且将返回 302。每个实际 Ariso GET 最多交付一次；普通展示和 download=1 共用一个指标。

只接收 original/compressed/watermark；实际默认链接回到 original 就计 original。thumbnail、所有者、private、预览、HEAD、304、拒绝及读取/签名准备失败不计数。本地开始后取消仍计一次；S3 后续远端失败无法撤回签发计数。分享大图的匿名预加载产生真实内容 GET 时也按相同规则计数，不声称这些数字代表看完图片的人数。

`recordAccess(event, timezone)` 是进程内同步聚合函数，不写 SQLite，不请求文件/网络。入口在事件发生并交付时读取 site 当前已提交的有效时区，不沿用等待文件首块或 S3 签名之前的旧配置快照；读取与同步聚合之间不插入 await，再以该时区同步确定 date + timezone 并纳入聚合键。不能到刷库时才套用新的时区。storageId 可用于诊断，不额外创建“各存储访问量”指标；本版存储图统计空间占用。

聚合不再次检查图片是否仍公开或存在：授权和计数条件由 delivery 在实际发生时判定。之后移入回收站、变私有或删除，不抹掉已经发生的访问。失败必须记录上下文且不阻断合法内容响应，不通过重试内容请求补计数。

## 4. 统计表与批量写入

| 表                       | 唯一键与内容                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| `analytics_daily`        | date + timezone + version；当天全站访问量，version 仅 original/compressed/watermark              |
| `analytics_image_daily`  | image_id + date + timezone；单图当天三版本合计，用于周期排行；索引支持日期范围聚合和指定图片读取 |
| `analytics_image_totals` | image_id；original_count、compressed_count、watermark_count 三个累计整数，只有实际访问后才创建   |

全站累计来自 image_totals 三列求和，按版本累计同样求和；单图累计从自身行读取。不再维护第四份全站累计副本。每日全站表避免为了趋势扫描所有单图每日行；单图每日表不保留未要求的每图每日版本维度。

统计 image_id 是历史身份，不设置对 media_images 的删除级联或阻止删除外键，不复制文件名、存储 Key、路径或 EXIF。图片 ID 永不重用；同名重新上传是另一张图片，不继承统计。零访问图片没有统计行，关联查询用零值表示。

内存按 imageId/date/timezone/version 聚合增量。工程起始值：每 5 秒尝试刷新，有 1000 个不同聚合键时提前调度，每次最多提交 1000 个键；剩余批次让出事件循环。使用预编译/参数化语句与短同步事务；一批同时增加每日全站、每日图片及图片累计。

事务明确提交成功后才从内存扣除该批增量；任何语句失败整批回滚并保留原增量，不能出现每日已加、累计未加。由于同步事务不穿插事件循环回调，无需为此创建通用消息确认协议；提交后的内存确认同样同步完成，不夹入 await。进程崩溃后不重放内存，因此已提交批次不会被启动恢复重复计数。

单个 Web 进程只注册一个定时器和聚合器，开发热更新不能重复启动。写入失败后降频重试并暴露最近错误/上次成功写入时间；不能每个图片请求都尝试刷库。工程起始缓冲上限 20000 个不同键，满且持续写入失败时保留已有增量，新键无法接收须记录漏计和统计不完整状态，不让无界内存拖垮图片服务。此值需真实压力测试，不是图片数量限制或产品设置。

正常关停应停止接收新请求、等待现有传输按服务器规则结束，在数据库关闭前刷完已接收增量。当前 Next 关停由框架处理，runtime 没有业务 shutdown 协调；实施任务必须核对当前版本退出顺序，不能另加 process.exit 与框架争抢。容器 SIGTERM 有界退出、SIGKILL 丢失未刷数据、刷库失败退出都需实际验证。正常不丢和异常只丢未持久数据是验收目标，本稿不是已有保证。

## 5. 日期、时区与 365 天

date 是事件发生时站点时区下的 YYYY-MM-DD，同时保存该 IANA 时区。日期计算复用 site 采用的成熟时区能力；夏令时日可能不是 24 小时，不能用固定毫秒差来截断当地日期。

改站点时区不移动已保存记录，也不改变已在内存确定的日期。相同日期不同 timezone 的行独立保存；展示按原有 date 标签合计，并在受影响范围标注“含按旧时区归档的数据”。不只筛当前 timezone，否则改设置会让历史消失。

例如上海时区 9 月 17 日 00:30 的一次访问保存为 9 月 17 日；随后改洛杉矶时区，新访问可能归 9 月 16 日。旧访问仍在 17 日，累计不变。“今日”取当前时区今天的日期标签，合计该标签的全部历史归档段；时区切换附近不声称等于按新时区追溯重算的精确 24 小时窗口。图表说明须能读到这一点。

每日记录保留所在 timezone 的当前日期及前 364 个日期，早于该边界的每日行可清理。清理分别按行所属时区计算边界，不用当前站点时区批量挪动历史。未来日期不因时区调整或机器时钟回退被删除；时钟校正不重写历史，异常记录日志。

累计在每次刷库时已经包含每日增量；每日记录老化后只删除每日明细，不能再把这批数字加一遍累计。这是“更早数据只保留累计值”的实现，不是访问量到第 366 天才进入累计。停机超过一年后再启动分小批清理；每批有界事务，重复执行不改累计。 初始化完成后调度一次保留清理，此后每小时检查各存量时区的日期；当地日期前进后执行当日清理，有界分批并让出事件循环，不与刷库批次重入。构建/迁移 CLI 不启动这些任务，不要求外部 cron。

## 6. 报表周期与热门图片

**已确认：** 7/30/90 天均包含今天，开始日为当地今天向前 N−1 个日历日。今天标记“截至当前统计更新”，不与完整一天混为一谈。缺少访问记录的日期补零，接口/数据库故障不补零。

趋势、热门图片和版本访问量随同一个周期选择一起变化，默认 7 天；今日/累计指标固定自身含义，空间图始终是当前占用，不伪造空间历史。2026-09-19 原型已改为共同周期并注明各块范围，实际数据联动仍须工程验证。

趋势直接读取 analytics_daily，原图/压缩/水印三种计数之和等于该范围总访问。热门取同范围的 image_daily 按总访问降序、imageId 升序的前 10 张；不包含零访问，不添加随机示例凑满。相册多重关联不参与访问表聚合，一张图加入三个相册也不计三次。

排行是所有者历史数据，不要求图片现在仍公开；改私有/存储停用的图片保留已发生的访问。名称实时关联当前 displayName；回收图片使用占位并链接到回收站记录，不能通过排行榜缩略图绕过回收规则。正常库中的图片内容仍按所有者 delivery 规则展示，读取失败不影响历史数字。

**已确认：永久删除仍保留历史数字。** 全站累计、历史趋势、版本计数不减少；相应日期仍在保留期内时，热门榜保留“已删除图片 + 短 ID”占位，无缩略图、原名、文件信息或打开链接。不为历史统计保留 media 图片实体或阻止清理。过了 365 天，该图每日排行明细消失，累计计数行保留。

例如一张图昨天有 500 次访问，今天永久删除：昨天趋势仍有这 500 次，累计不降，最近 7 天热门可显示“已删除图片”。正在内存等待刷入的删除前访问同样允许按历史 ID 入库，不因查不到 media_images 而丢弃；删除后拒绝的新请求不计数。

## 7. 当前数量与对象占用

### 7.1 数量

**已确认：** 主指标“图片数量”只计正常图库中的资产，包含 public/private、pending/processing/failed 和存储停用，不包括回收/永久删除中的图片。旁边单独显示回收站数量。相册数量包含空相册、没有开启分享的相册；标签不是相册，不用关系行数当图片数量。上传尚未交接为 media 资产时不算图片。

工作台已有处理异常入口使用真实 media 状态：初次处理失败和 ready 图最近重处理失败分别说明；只统计仍未解决的当前异常，不把终态历史失败任务全部累加为“失败图片”。点击进入已有查询或具体详情，不虚构 library 尚未定义的筛选参数。

### 7.2 空间

空间从各提供方的真实对象责任记录聚合，各存储分别展示；没有访问也占空间，停用不清零。单位以字节入库、界面 KiB/MiB/GiB，不把 S3 Bucket 总容量、其他软件文件、SQLite/WAL/日志或系统剩余磁盘当作 Ariso 图片对象占用。

使用互斥组成，按下列优先顺序为每个物理对象分组，一份对象只计一次：

| 分组           | 内容                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 回收站         | 归属于回收资产的全部未确认删除对象，含原图、派生、候选、旧对象及删除失败；不再同时放进下面各组     |
| 正常原图       | 正常资产当前 original 指向的已存对象                                                               |
| 正常派生       | 正常资产当前 compressed/thumbnail/watermark 指向的已存对象                                         |
| 处理中／待清理 | 正常资产的其他候选/旧对象、upload 尚持有责任的临时/正式候选及 storage 探测对象；按当前责任归属去重 |

planned 且尚未开始写入的对象是零已占用；writing 或是否落盘未确认则显示待核对，不能按计划的文件大小冒充已写入。stored、cleanup_pending、cleanup_failed 的已确认字节仍计入，只有成功删除/明确确认不存在才去掉。回收和恢复只改变组成，不能使总量翻倍或凭空减少；永久删除受理时仍占空间，逐对象成功清理后再减少。

每个对象身份使用 storageId + objectKey。upload 向 media 的正式交接按已有同一事务转移责任；已交接的 upload 审计记录不再贡献同一正式 Key，但未清理临时 Key 仍贡献。不能简单把 media_versions 四行相加漏掉遗留对象，也不能把 media_objects 与版本表当两份文件累加。

provider 返回已确认字节、待核对对象数和确认时间/状态。界面为“已登记占用 X，另有 N 个对象待核对”，未知不显示成零，不将带未知部分的图表画成完整 100%。全部已确认时才显示完整组成比例；部分已知时图例注明比例仅涵盖已知字节。

这不是每次访问统计页就遍历 Bucket 的实时账单。业务写入/删除时更新对象记录，失败或在途对象由所属模块核实；analytics 只读取。外部手工删文件/改 Bucket 后，在提供方发现之前数据可能仍为最后确认值，说明基于对象记录，不声称已扫描远端证明准确。不新增无依据的全 Bucket 扫描或新的文件清理器。

`${DATA_DIR}/tmp` 中转/处理工作文件、品牌/水印素材和数据库文件不属于配置存储内图片对象组成；不折算进某个 S3 或本地图片存储。页面说明范围，宿主机实际磁盘占用可高于此值。相关空间不足仍由 runtime/upload/media 各自处理，不能用此图表代替实际可用空间检查。

## 8. 查询接口、更新与权限

| 入口（草案）                          | 返回                                                                                                                |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `GET /api/analytics/overview?days=7`  | 当前图片/回收/相册数量，今日/累计访问、趋势、热门、版本量及本次查询范围；days 仅 7/30/90                            |
| `GET /api/analytics/usage`            | 各现存存储当前互斥组成、已知字节/待核对数、启停状态和最后核实信息；不含凭据或对象 Key                               |
| `GET /api/analytics/images/{imageId}` | 已存在图片的累计与最近 7/30/90 天合计，供所有者详情；回收记录可读统计，无内容读取特权；已永久删除由排行历史占位体现 |

所有入口复用 identity 所有者验证，拒绝匿名、上传 Token 和分享授权。响应 private/no-store，无公共统计脚本；不从外部 POST 接受客户端上报访问量。输入非法 400、无管理会话 401、指定图片记录不存在 404；真实读取故障返回错误和可诊断日志，不把故障变成成功零值。

同一 overview 在一个短只读事务内查询已持久统计和当前数量，返回 generatedAt、lastFlushedAt、timezone、范围、是否含旧时区段及统计健康状态。不把不同刷新轮次的累计和趋势随意拼成同一响应；不为打开报表强制刷库或合并正在变化的内存增量。页面数据因此通常延迟一个刷库周期，不能声称严格实时。

读取页面可见时每 10 秒刷新，隐藏时暂停，重新可见立即读取；不叠加未结束请求。切 7/30/90 时更新查询标识和 URL 的 days，忽略旧请求的迟到结果。保留旧数字等待刷新可以，但须标加载/上次更新时间；失败明确标旧数据，未获取过数据就显示错误而非零。

lastFlushedAt 是本进程最近实际提交成功的批次时间，重启后尚无成功批次时为 null，不拿启动时间冒充；没有新访问和真实空库不因此报异常。健康状态区分无待写数据、正常等待、失败积压和已发生漏计。进程内发生漏计后保留不完整标记，后续刷库成功只消除积压，不能抹去损失事实；重启后无法追溯未落盘损失，页面始终说明近似统计及异常退出可能损失少量访问，不宣称已恢复精确完整历史。不为此另建逐请求账本。

统计积压/持续失败时显示延迟或不完整提示；空间待核对是空间数据状态，不能误报为访问计数故障。空库真实零值、正常范围无访问、读失败和统计暂不可用均需不同状态。退出登录清理管理查询缓存。

## 9. 提供方与工程组织

拟放 `src/server/analytics/` 的 schema、collector、retention、queries 和输入/响应定义；单元及集成测试各有 analytics 目录。累计/每日更新复用一个批次函数，定时器与正常退出均调用它；不同入口不各写一套加法。

analytics 对外提供 `recordAccess`、`flushAccessBatch`、`pruneDailyStats`、`readOverview`、`readImageStats`。函数接收现有连接/事务和显式时钟便于测试，不建立新数据库连接，不引入通用事件总线。图片详情的统计由页面入口组合 analytics 与 library，避免 library 与 analytics 互相依赖。

示意批写边界，实际表结构和测试由实施任务创建：

```ts
const batch = collector.nextBatch(1000);
db.transaction((tx) => writeAccessIncrements(tx, batch));
collector.acknowledge(batch);
```

media 提供正常/回收/当前处理异常数量及所属对象占用；collections 提供相册总数；storage 提供配置展示信息与探测对象占用；upload 提供仍承担责任的对象占用。每个提供方定义互斥对象状态与只读聚合契约，组合入口在同一读事务中汇总给 analytics 格式化。upload 接口缺失时不能显示“完整占用已通过”；其接入依赖放在对应实施任务，不把所有计数任务都锁到上传实现之后。

起始索引按查询建立：全站每日按 date 范围、单图每日 date/image_id 与 image_id/date、累计主键；先验证实际查询计划，不把所有可能字段都建索引。十万图片规模要包含持续一年访问的热点与长尾，不能只建十万图片却只有十条统计行。测热门范围聚合、清理与刷库同时进行时的响应；必要索引/SQL 优化由证据决定，不预先引入分析数据库。

ANALYTICS-COUNT 先接本地 delivery 与聚合/日期，再覆盖 S3 和完整排除矩阵；ANALYTICS-REPORT 接当前用量、图表与历史对象状态。完整空间组成必须依赖 upload 的责任交接和 storage probe，关停计数必须依赖真实 Next/Docker 验证。技术验证是工程任务，不要求用户凭场景批准其正确性。

## 12. 用户确认记录

1. **图片数量。** 已上传 100 张，其中 10 张在回收站、5 张处理失败。已确认主指标显示“90 张图片”，旁边显示“回收站 10 张”；失败的 5 张仍算图库图片。空相册也计入相册数量。
2. **删除热门图片。** 一张图昨天被访问 500 次，今天永久删除。已确认历史趋势和累计保留这 500 次；最近 7 天热门榜若仍入榜，显示“已删除图片”，不保留缩略图或旧文件名。这样删除文件不会让过去访问量减少。
3. **切换统计周期。** 从 7 天切到 30 天，已确认趋势、热门图片和版本访问量一起切到含今天的最近 30 天；“今日”“累计”和当前空间占用保持各自含义。今天尚未结束会明确标注。

空间去重、未知占用说明、批写重试、365 天和旧时区处理属于已批准规则的工程闭合，不再重复确认。用户于 2026-09-17 确认上述三项，十份业务规格的逐份产品评审完成；代表原型现已补充，当前按设计交接形成全部实施任务与真实依赖门槛。upload 技术前置及本稿工程验证仍需实际证据，不能因十份规格通过而提前关闭。
