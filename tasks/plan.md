## 1. 结论与边界

采用单个 `*.zip.age` 文件：内部 ZIP64 保存数据库、全部必要对象与素材，外部标准 age v1 进行整包密码加密。新增一个进程内工作线程执行归档和加解密，继续使用现有 Web 服务、SQLite、存储适配器与初始化码，不增加部署服务。

备份采用两阶段准备：先拒绝新的内容修改，让已受理的前台修改及其依赖任务完成；再暂停后台持久任务和清理，等待正在执行的批次结束。浏览、会话、访问统计与临时预览继续工作。

恢复在空实例中先准备数据。全部本地和新 S3 内容完整后提示重启；下一次启动在打开正式数据库之前完成文件与数据库切换，再进入现有启动流程。页面可打开与恢复操作授权分开处理。

用户先授权本地闭环，随后授权继续实现 S3，均暂不发布部署。当前归档读取包含停用 S3 的持久对象，新目标配置、当前版本测试、流式复制与页面流程已接入；小样本真实提供方、浏览器和故障复核已完成，准确范围以实施记录为准。准备期限采用 60 秒内部默认。用户本轮明确不做大文件和容量压测，只使用小样本验证功能；历史格式规模证据保留，不外推真实服务容量。

## 2. `/setup` 的访问与恢复授权

### 当前行为

项目没有定义 `/step` 路由。正式初始化页是 `/setup`：未初始化时可匿名打开，有所有者时跳转 `/login`。`POST /api/setup` 在提交时和最终写事务内验证启动日志中的初始化码，成功后销毁当前码。恢复接口现已接入，同样逐请求验证当前初始化码。

依据：[页面](../src/app/setup/page.tsx)、[初始化提交](../src/app/api/setup/route.ts)、[初始化状态](../src/server/identity/setup.ts)、[恢复接口授权](../src/server/backup/http.ts)。正式恢复授权已有真实 handler 和双实例 HTTP 检查；原型演示校验不作为鉴权证据。

### 正式恢复入口

| 场景                                  | 页面和接口行为                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| 未初始化的 `/setup`、`/setup/restore` | 可显示入口、初始化码和文件选择表单；不匿名返回备份内容、任务详情或存储凭据           |
| 已初始化                              | 页面转登录；恢复 API 返回 `409 SETUP_ALREADY_COMPLETED`，不开放覆盖恢复              |
| 初始化码错误或缺少                    | 恢复 API 返回 `401 INVALID_SETUP_CODE`，不读取大请求体、不创建上传文件、不测试 S3    |
| 当前码正确且目标空白                  | 可创建、查询、上传、解密、配置目标、执行、取消或重试本次恢复                         |
| 准备阶段服务器重启                    | 任务成为 interrupted；重新输入本次启动日志中的码后可读取原任务，不把旧码当作长期凭据 |
| 恢复启用完成                          | 初始化入口关闭，使用恢复后的所有者账号登录                                           |

恢复请求将初始化码放在 `X-Ariso-Setup-Code` 请求头，不放 URL 或日志。创建任务前先提交小请求完成授权；上传文件的请求自身也必须先验证，不能把任务 ID 当作凭据。备份密码只用于解密，不能替代初始化码；知道密码不意味着能向任意新实例写入数据。

第一版不另建恢复 Token。页面会话在内存中保留初始化码；刷新后重新输入当前码即可读回原任务，已经开始的服务器任务继续运行。重启进程会换码。这个重新授权步骤是正式接口行为，原型中直接恢复进度不代表免认证。

正常初始化与恢复创建共享一个进程内初始化占用对象。恢复创建在第一次异步文件操作前同步占用；正常 setup 在哈希前及最终同步写事务内检查占用。重启从未结束恢复记录重建占用，但显示为中断及可重试/放弃，不谎称旧进程仍在运行。

“空白”允许启动生成的数据库、空目录、默认配置及自动产生的 `storage_scans` 运维记录；不得存在所有者、图片、相册标签、分享等用户业务数据。原本地目标目录不能包含待覆盖的业务文件。备份暂存目录本身不使实例变为已初始化。最后启用前再次检查目标仍符合这一条件。

## 3. 备份格式与加密

### 3.1 格式选择

| 层       | 选择                                                         | 原因                                                      |
| -------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| 归档     | 现有 `zip-stream@7.0.5`，`forceZip64: true`、`store: true`   | 支持大文件和大量条目，复用现有流式写入；图片不重复压缩    |
| 密码封装 | 标准二进制 age v1，文件名 `ariso-<UTC时间>-<任务ID>.zip.age` | 整个 ZIP 都在密文内，文件名和清单不会通过 ZIP 目录泄露    |
| 加解密库 | 已安装 `age-encryption@0.3.1`，即官方 Typage 实现            | 已验证 ReadableStream 及官方 age CLI 双向互通             |
| 解包     | 已安装 `yauzl@3.4.0`，开发类型 `@types/yauzl@3.4.0`          | 已验证 ZIP64 中央目录与逐项文件流                         |
| 执行位置 | 单个 `worker_threads` 工作线程                               | Typage 的 scrypt 同步计算会占用线程，放在主线程会影响浏览 |

上述新增依赖已锁定并通过冻结安装，没有升级原有依赖。A01 已通过功能与互通实验；正式模块和独立 worker 已接入，并通过实际 standalone 双实例 HTTP 备份与恢复。包纯净性与容器结果单独记录，不能以构建成功替代。age-encryption 为 BSD-3-Clause，yauzl 及其类型包为 MIT。

密码模式使用 age 的 scrypt：`logN=18`、`N=2^18`、`r=8`、`p=1`、32 字节派生结果；盐、文件密钥与负载 nonce 均由库生成，不自行生成或复用。负载使用标准的 64 KiB ChaCha20-Poly1305 分块和终块认证。标准规定的头部信息可见，站点内容和文件名均位于加密负载中。

密码原样作为 UTF-8 输入，不裁剪空白或偷偷规范化。要求非空且两次输入一致；不新增复杂字符组合规则。密码不写任务记录、数据库、日志、文件名或下载 URL。任务结束释放引用并结束工作线程，不承诺 JavaScript 能可靠擦除所有内存副本。

Typage 当前解密实现允许到 `logN=20`，并没有公开的较低解密上限参数。Ariso v1 只接收自己生成的单 scrypt、`logN=18` profile：启动 KDF 前，以最多 1 KiB 的头部读取检查版本、单 stanza 类型和工作因子，随后交给库完成完整解析和认证。不实现另一套 age 解密器，不读取私有类来修改库行为。

`logN=18` 的算法工作区约 256 MiB，另有运行时、条目元数据和流缓冲；这不是峰值内存承诺。Node 24/macOS arm64 独立实验中，4 GiB 单项加密约 469 MiB RSS，十万对象加密约 1.1 GiB RSS。正式服务还会有图库和后台占用，不能承诺 512 MiB 或 1 GiB 容器足够。单实例只执行一个归档/解密任务；不在主线程计算 scrypt，不因为内存紧张静默降低工作因子。

未选 ZIP AES：常见方案按条目加密且保留 ZIP 结构，不直接满足整包保护。未选单个自定义 AES-GCM 大流：单消息有约 64 GiB 上限，再分块就需要自行设计 nonce、顺序及截断协议。未选 age 原生 CLI：需要额外二进制及跨架构打包，其口令输入与 Web 集成也增加进程管道工作。

依据：[age 规范](https://c2sp.org/age@v1.1.0)、[Typage API](https://github.com/FiloSottile/typage/blob/v0.3.1/lib/index.ts)、[scrypt 实现](https://github.com/FiloSottile/typage/blob/v0.3.1/lib/recipients.ts)、[yauzl 文档](https://github.com/thejoshwolfe/yauzl)、[NIST GCM 规范](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=51288)。

### 3.2 ZIP 内部内容

```text
manifest.json
database/ariso.db
secrets.json
assets/branding/<key>
assets/watermarks/<key>
objects/<storageId>/<objectKey>
```

`manifest.json` 只保存小型摘要：`formatVersion=1`、应用版本与修订、数据库迁移版本、数据库副本生成起止时间、存储列表、图片数量、对象数量和字节总量。具体对象清单来自副本数据库，不再复制一份可能与数据库分歧的巨大 JSON 数组。

`secrets.json` 仅保存解密既有业务配置所需的原 `ARISO_ENCRYPTION_KEY`。不复制整个环境文件，不带走无关环境秘密；新实例继续使用自己的 `BETTER_AUTH_SECRET`。数据库中的会话和一次性凭据另按归整规则处理。

ZIP 只写普通文件，使用 UTF-8 名称；路径由存储 ID 和对象 Key 构造，不用用户原始文件名作为磁盘路径。原始名字、图片身份和关系由数据库保留。ZIP 条目允许任意顺序，导入按名称匹配，不依赖临时构建目录或条目排列。

包内不含程序、镜像、node_modules、日志、已有备份、运行临时目录和本次控制记录。第一版不接受多卷 ZIP、其他归档格式或未定义的 formatVersion，不添加兼容猜测和文件格式回退。

### 3.3 完整性与暂存

备份从数据库副本和对象流直接输出 ZIP，再输出 age 密文；不先在源站生成一个完整明文 ZIP。Node 转 Web ReadableStream 显式用 `chunk.byteLength` 计量队列，并设 64 KiB 高水位，避免默认按块数计算缓冲。必须等 ZIP 中央目录、age 终块、文件同步、`.part` 改名及父目录同步完成后，才标记 ready。

恢复先完整保存密文，再完整解密到私有暂存 ZIP。age 解密流全部成功、终块已验证，才将暂存 ZIP 标为可用；流前面输出的明文不能提前被当作有效恢复内容。yauzl 需要 ZIP 末尾中央目录，不能把它当作任意顺序的流式解包器。

读取摘要时验证 profile、中央目录、必需条目、数据库关系及对象路径/大小清单；逐项恢复时用 ZIP 自带 CRC 和实际字节数检查内容。Node 24 的 `zlib.crc32()` 已核实可用。yauzl 不自动验证 CRC，应用须在读取流中完成；不另加重复 SHA 清单、签名或封条。

解包只接受本格式定义的普通文件，拒绝重复名称、逃出暂存目录的路径、文件/目录冲突、ZIP 条目加密或不支持的压缩方法。符号链接和归档自带权限不是本格式内容，不予恢复。验证依据是实际导入边界，不重新验证每一步成功的内部操作。

已验证真实 4 GiB＋1 MiB 单项和 100000 个对象（加 manifest 共 100001 条目）。这不等于十万张各带多个版本的图片；容量按对象及版本总量估算。zip-stream 底层中央目录集中输出造成明显峰值。临时用 yazl 3.3.1 做相同样本两轮对照，峰值仍有 839–894 MiB 且写出约慢四倍，因此本轮不增加另一套 writer。保留现有实现，正式产品阶段须在目标容器测量内存预算；yauzl 数值范围和文件系统也有上限，不承诺任意规模。

## 4. 任务状态、目录与资源

不用新数据库表存放归档任务。采用每任务目录与原子更新的 `state.json`，这样恢复替换业务数据库时不会丢失控制状态，也不会把旧备份历史导入新站。

```text
DATA_DIR/backups/<id>/
  state.json
  snapshot.db                  # 完成后清理
  ariso-...zip.age.part         # 不可下载
  ariso-...zip.age              # ready 才可下载
DATA_DIR/restore/<id>/
  state.json
  remote.json                  # 新 S3 位置、加密凭据与清理责任
  remote-plan.json             # 本任务将写入的远端对象清单
  source.zip.age.part / source.zip.age
  content.zip.part / content.zip
  work/ariso.db
  ready/ariso.db
  ready/storage/
  ready/assets/
  previous-empty/               # 启用期间移出的空实例内容
```

目录与文件采用应用私有访问权限。`state.json` 保存任务 ID、状态、阶段、时间、计数、文件名和大小、待清理标记及错误。S3 的位置、配置 revision、测试和清理状态保存在 `remote.json`，新凭据使用新实例密钥加密；`remote-plan.json` 保存该任务的对象写入清单。任务记录不含备份密码、初始化码、明文存储凭据或原解密密钥。关键状态按写临时文件、fsync 文件、改名、fsync 父目录更新；文件同步不能代替目录项同步。不建立额外日志数据库或签名机制。[fsync 说明](https://man7.org/linux/man-pages/man2/fsync.2.html)

备份状态：`preparing → copying → finalizing → ready`，失败为 `failed`，主动取消为 `cancelled`，进程退出为 `interrupted`。同一实例最多一个进行中的备份；旧 ready 文件保留至用户删除。正在下载的文件拒绝删除并说明原因，避免一个操作中断另一个已确认下载。

恢复状态：`receiving → received → decrypting → configuring → restoring → ready → activating → completed`。活动阶段失败或中断分别记录 `failed/interrupted` 与 `failedPhase`，保留可诊断结果；重试不是自动断点续传。

关键规则：

- 当前页面中的分块请求失败可查询已接收偏移再重试；刷新或进程重启后，未完成文件重新上传，不承诺跨重启断点续传。完整密文在密码错误时保留。
- 解密中断需要重新输入密码，从阶段起点重新解密，不保存密码以自动续跑。
- 已完整解密并验证的 ZIP 可继续用于配置和复制；先持久化 configuring 再删除源密文，避免清理后重启仍只知道解密阶段。配置和执行在旧阶段清理尚未结束时等待它退出，再重新检查状态。
- 开始复制后，目标位置固定。同一任务重试向同一目录/命名空间重写，不创建新图片 ID；不按未经验证的旧进度跳过对象。
- 改目标、换备份或放弃恢复需终止当前任务，列出旧暂存目录及远端已写前缀；仅清理本任务拥有的内容，失败保留路径和重试入口。
- `ready` 后清理不再需要的明文 ZIP/工作文件，保留最终准备数据。启用重试不依赖原服务器、原 S3 或备份密码。
- 页面关闭不取消服务器任务。取消先持久化 cancelled 与 `cleanupPending`，再等待工作线程和文件流真正结束，防止取消 ready 时崩溃后误启用。清理失败保留初始化占用、诊断和重试入口；清理成功并持久化后才释放。重启仍识别待清理标记。强制结束线程只用于该备份/恢复任务，不杀掉整个 Web 服务。
- S3 变更开始前持久化整体 `pending` 判别联合，区分 PUT（key、startedEmpty）与 DELETE（key）；没有待确认操作时整体清空。已观察到 PUT 提交后先持久结算 PUT，再登记删除。未确认 DELETE 不重复发送；对象仍在则保留责任，对象消失才可结算，避免迟到的旧删除影响后续任务。完整 PUT 已发送但 SDK abort、断线或 5xx 未确认时，不能凭空 LIST 清除责任；保留 `cleanupPending` 与初始化占用，并返回 `RESTORE_REMOTE_WRITE_UNCERTAIN`。稍后重试发现并删除迟到对象后才解除；明确 4xx 拒绝或不足声明长度的未完整发送可以结算。若服务一直不给确定结果且对象始终不出现，保持待清理并引导检查该 namespace 与服务日志；不加入“等待 N 秒即成功”或人工忽略入口。

源站备份空间估算为全部必需对象和素材、数据库副本、ZIP/age 开销及运行余量。恢复设密文 E、明文 ZIP Z、本地恢复内容 L，及时删除源密文后的主要峰值为 `max(E + Z, Z + L)`，再加数据库和运行余量；S3 内容直接从 ZIP 写到新 S3，不另保存全量本地副本。

开始前显示估算并检查可用空间；过程中仍处理真实 ENOSPC。不能把一次空间检查当作空间保证，也不先引入可调并发/压缩/分卷配置。流复制先采用单对象并发，后续只有测得瓶颈才调整。

### 4.1 恢复文件的上传边界

现有 `src/cli/http.ts` 将请求接收期限设为 31 分钟，`request.setTimeout()` 的空闲计时不能替代这一总接收期限。保留该设置，不为恢复改动所有请求的行为。[Node HTTP 文档](https://nodejs.org/docs/latest-v24.x/api/http.html#serverrequesttimeout)

恢复上传使用顺序分块 PUT，第一版块上限 8 MiB；整个文件可以跨越许多请求，总耗时不受单次 31 分钟约束。前端用 File.slice 和现有浏览器 fetch，服务端复用流接收方式，不引入全站上传框架或新的图片上传协议。

- 每块仍先验证当前初始化码。请求携带 `Upload-Offset` 和 `Upload-Length`，内容是该区间的字节；服务端限制实际块长度，并核对总长度。
- 同一任务同一时间只接收一块，只有 offset 等于已完成偏移才写入 `.part`。完整收到本块后更新偏移并响应；重复/乱序块返回 409 和当前偏移，不重复追加。
- 块中途失败截回本块起点；前端查询服务端进度后用同一 File 对象重试。响应丢失时也先查询，不凭客户端进度猜测是否已收到。
- 刷新后不按文件名/大小猜测仍是同一个源文件。重新选择文件并显式重置未完成接收，再从 0 上传；服务器重启后同样处理未完成接收。重置先禁止新块、停止并等待当前块的接收及文件写入完全退出，随后才截断文件、清零偏移并重新开放接收，防止旧请求继续写入重置后的文件。
- 全部字节收到、同步文件及最终改名/目录完成后才持久化 received；这仍不代表密码或内容已验证。

每块仍服从现有期限，连接故障明确报错。部署代理的单请求体限制需至少允许此块大小，并按现有长请求操作指南检查空闲超时；不承诺任意代理默认值均可上传。隔离实验已用真实 HTTP、8 MiB 分块和缩短至 1.5 秒的 requestTimeout，验证累计传输超时长而每块成功；单请求负向对照被中止。正式 D02 接口已覆盖鉴权优先、分片、重置与重启后的重新上传；真实 31 分钟传输和部署代理仍需另行验证。

## 5. 暂停修改的具体实现

### 5.1 两阶段准备

新增由现有 ServerRuntime 持有的 `contentMutations`：

```text
run(label, operation)            # 同步检查准入、登记；finally 释放
closeAdmission()
waitForIdle(signal)
openAdmission()
```

管理接口的 Cookie/Origin 鉴权先执行，随后进入 run，再读取会产生业务状态的大请求体或创建记录。实际匿名邮件重置 POST 在整个 Better Auth handler 外登记，以免先消费 Token 后才被暂停；这一凭据接口暂停优先，暂停后 Token 保留。同一个已准入操作内部不重复登记，不因为进入准备阶段而把它自己的后续步骤拒绝。

1. 同步关闭新内容修改入口，开始单一准备期限；UI 显示暂停修改。
2. 媒体队列继续运行，等待已受理的前台内容修改结束。公开上传的登记覆盖接收、交接和 `waitPublicUpload()` 全程。
3. 前台操作结算后，暂停后台领取新的持久任务和发起新清理；等待当前持久任务和当前清理批次结束。队列中未领取的任务不要求清空。
4. 显式刷写当前待提交统计，然后通过 `db.$client.backup()` 生成一致副本；后续统计和会话继续运行，副本时间以实际完成信息说明，不承诺点击按钮那一毫秒。
5. 工作线程只根据副本清单读取持久文件，直到归档完成、失败或取消。结束后恢复调度与准入。

准备期限为 60 秒，作为内部工程默认，不加用户设置项。超时只让本次备份失败并恢复操作，原上传/处理继续，不取消正常业务请求。现有 PicGo 等待上限 900 秒保持不变。这明确解决“请求等待派生任务，而备份先暂停该任务”的相互等待问题。

各后台服务新增 `pause()`、`waitForIdle(signal)`、`resume()`，复用现有 active/cleaning 集合；不通过 stop/start 暂停，避免 abort 和重复启动恢复。

### 5.2 允许与暂停的边界

| 类别           | 暂停                                                                        | 继续                                                              |
| -------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 上传           | 新提交、接收、完成交接、重试、取消与清理请求；公开上传 API                  | 已准入请求的完整执行、进度查询；已有 S3 签名只写临时对象          |
| 图片/集合      | 改名、可见性、替换、尺寸生成、重新处理、回收/恢复/永久删除、相册标签修改    | 查询、选择 POST、复制链接 POST、状态 POST、图片读取及已有版本下载 |
| 分享           | 新建、修改、撤销、轮换 Token                                                | 分享浏览、密码解锁 POST、grant 维护与过期判断                     |
| 配置/素材/存储 | 配置修改、品牌水印上传、连接/CORS 测试、扫描和清理重试                      | 配置查询、已有素材读取、备份自己的维护读取                        |
| 身份           | 邮箱/密码修改、Token 管理、GitHub 新绑定/解绑、实际邮件重置密码提交         | 登录、退出、会话续期、已绑定 GitHub 登录、找回邮件申请与链接页面  |
| 后台           | 持久媒体任务领取、对象永久/候选清理、上传维护、存储扫描、探测维护、水印清理 | TIFF 等临时预览、预览维护、统计、分享授权维护                     |

不能按 GET/POST 分类，也不能在 `requireOwnerSession` 上一刀切拒绝。新增错误统一为 `409 SITE_BACKUP_IN_PROGRESS`，由现有模块错误响应明确透传，不变成 500。详情和菜单都说明暂停原因；后端检查才是操作边界。

GitHub 绑定还有备份前发起、备份期间到达的 GET callback。在现有 auth adapter 的 GitHub account 新建位置检查 gate，已有绑定的登录更新继续允许。实际密码重置 POST 单独登记，不封整个 Better Auth handler。

CLI 密码重置保留为紧急运维例外：它只改变 SQLite 认证数据，副本会捕获事务前或事务后的完整状态，不因它增加跨进程暂停锁。页面的账号修改仍按表中规则暂停。人工直接改库、改文件或在服务商控制台改对象不属于本协调器控制范围；备份期间不得对必需对象进行这些外部修改。

### 5.3 后台与退出

`media/queue.ts` 暂停时仍领取 preview，只停止持久任务和持久清理。upload、storage maintenance/probe、watermark 各自暂停下一批；branding 等待当前 ready/active，不 close 掉读取能力。analytics、sharing 和临时 preview 保留。

旧 S3 签名不可撤回，但只作用于 uploads/probes 临时 Key。阻止新签名和新的正式交接，等待已开始交接完成；临时迟到对象不进备份，正常恢复运行后由已有扫描清理。无需等待所有签名过期。

取消复制只取消备份工作线程的读取、归档和加密，等真正退出后才解除冻结。正常关停先关闭备份任务，再走现有服务关停链。异常重启没有旧工作线程，内存暂停自然解除；持久状态标为 interrupted，`.part` 不提供下载，不能依据旧记录重新永久暂停站点。

## 6. 数据库副本与对象清单

只在副本中归整运行状态，源库不因备份清空任何记录。副本清理后执行 SQLite integrity/foreign-key 检查，再枚举：

- 当前 `media_versions` 与 `media_size_versions` 的保存对象；正常和回收站图片同等覆盖。
- 持久 queued/待重试任务需要的原图、替换候选、尺寸源对象和已经保存的候选文件。
- 当前品牌、水印配置与持久任务引用的素材。

queued 保留其参数和重试时间，failed 保持失败。永久删除中的记录保留清理语义，不能复活为普通图片；已经不存在的待清理对象不强制补入包。必需版本或持久任务依赖丢失则备份失败，不跳过后显示成功。

不延续浏览器上传、探测、临时预览、旧会话、verification 和单次分享 grant；删除这些临时引用时保持外键与持久任务关系。不能把旧 `temporaryPath` 或源站临时清理责任带到新机器。当前媒体处理可从存储中的原图/候选重新读取，不需要复制所有 tmp。

停用存储也要备份。增加明确的维护读取入口，复用现有 Local/S3 文件读取核心，不临时修改源站 enabled 字段。停用的标志保留到恢复后的正式配置；源存储不可读时，完整备份失败并指出来源。

按副本数据库迭代清单，以 ZIP 条目名定位对象。不扫描整个 bucket，也不复制无引用的任意文件。无需把所有媒体条目装进主线程数组。

## 7. 恢复准备与新 S3

本地准备、S3 目标配置与复制、配置换钥及启用均已接入。下列规则对应当前实现；小样本提供方、浏览器、取消与未知变更的专项复核已完成，见 [S3 实施记录](../docs/verification/backup-implementation/s3.md)。

收到完整文件后，由工作线程解密并检查格式。摘要出现前完成 age 认证、数据库可读性和迁移版本匹配，以及必需文件清单检查；文件流的 CRC/实际长度在复制时逐项检查。界面明确“备份文件校验通过”和“恢复后完整性检查完成”两个阶段，不能把上传 100% 当作恢复完成。

保留 storage ID、image ID、object Key、相册标签和分享身份。每个原 S3 绑定一个新目标；同一 bucket 可用新的空前缀，不要求整桶为空。新命名空间须为空，或属于同一恢复任务的重试。不得直接指向仍在线原站的命名空间。

新凭据验证后，用新实例密钥写入工作数据库。连接测试结果必须对应新配置 revision；旧 CORS 结果清空，未通过新检测时沿用现有服务器中转上传。原默认存储和启停意图保留；恢复写入使用独立目标上下文，不自动启用正式停用存储。

每个新目标使用 `pathPrefix/ariso/<原 storageId>/`，不生成替代逻辑 ID。保存配置后只有 `testStatus=passed` 且 `testedRevision=revision` 才能执行；页面尚有未保存修改时也不能继续。取消或测试清理存在遗留对象时，只允许在原坐标修正凭据；不能借修改配置把旧位置的清理责任丢掉。R2 的整 Bucket 无锁规则由所有者明确确认，与自动测试结果分别记录。

配置转换仅处理现有三个配置表的四个加密字段。S3 使用新凭据；GitHub Client Secret 与 SMTP Password 用包内旧密钥解密、再用新密钥加密。保留账号密码哈希、上传 Token 和分享记录；删除旧登录会话及未消费验证凭据。新站公开地址由用户确认，复用现有地址校验和 CORS 失效逻辑。

小范围失败重试直接重写同任务的目标对象。本地完成文件写入与 CRC/长度检查后 fsync，再改名并同步父目录；S3 使用已有对象写入能力。S3 对成功写入的对象不再逐个重复下载验真；归档流验证、已返回的写入结果和最终清单核对各自承担责任。

工作线程完成全部复制、检查关系与配置解密、生成独立 `ready/ariso.db` 并关闭工作连接；本地文件及目录项同步后，等待远端写入确认及最终清单核对。主协调器等待线程真正退出后才发布 ready，新站后台清理仍未接触准备内容。线程退出不代表一个未确认的 S3 PUT 不会迟到写入，取消清理需要保留该项责任。

## 8. 重启时启用

启用必须在 `startup/preflight.ts` 的 `initializeRuntimePaths()` 和 `openRuntimeDatabase()` 之前。先只创建并检查 DATA_DIR 根目录、计算恢复路径，完成启用后才初始化正常业务目录。否则中断后重启会自动重建 storage/assets 占位目录，破坏改名步骤的重放。不能放在已经开库的 prepare 回调或 server-start 中。

1. 找到 ready/activating 任务，校验当前运行版本与准备库；以当前环境密钥检查已转换配置可解密。只有首次 ready 转 activating 前检查目标空白；activating 重放不把本任务已发布的数据库误判为已有站点。持久化 activating 后开始短步骤。
2. 将原空实例的 `storage`、`assets` 移到本任务 `previous-empty`，再把 ready 中的对应目录改名到正式位置；同步每次改名涉及的父目录。ready 源仍存在且正式目标为空位时继续移动；ready 源已不存在且正式目标存在时视为本任务已移动完成，但仍补齐源、目标父目录同步，覆盖上次刚改名就被终止的情况。原空目录本来不存在时不伪造它；无法由这些固定路径解释的冲突保留诊断，不覆盖其他内容。
3. 将原空 `ariso.db` 及存在的 `-wal`、`-shm` 一并移出。旧 WAL 不得留在新数据库旁边。
4. 从保留的 `ready/ariso.db` 复制到正式目录临时文件，fsync 后原子改名，再同步正式目录。保留该小型副本供启用重试，不额外复制全部媒体；旧数据库和 WAL 的移出也要同步涉及的目录。
5. 所有正式文件及目录发布均已同步后，持久化 completed，随后初始化正常业务目录并进入现有迁移、配置预检与 Web 启动。只在 completed 以后启动媒体、上传和孤儿清理。

步骤 4 后、completed 前中断，下次启动重做同一次发布；正常业务尚未启动，不会覆盖新站后续上传。启动看到 completed 时先同步该状态文件及父目录，覆盖上次在完成记录改名后、目录同步前终止的情况；随后只走正常启动，不再次发布准备库。失败的正常启动仍沿原启动诊断处理，不回到覆盖数据的分支。

A02 使用真实 SQLite WAL/SHM、文件目录 fsync 和 27 个实际 SIGKILL 检查点，共 36 项通过；已验证 completed 后新增记录及改密不被重放覆盖。正式 activation 回归另含 24 个真实 SIGKILL 检查点，验证接入后的相同发布边界；实验与正式用例数分别记录。SIGKILL 不等于物理断电，容器结果见实施记录。

启用中途失败时启动退出，日志包含任务 ID、步骤和相关路径，下一次重启继续。这一阶段没有正常网页可查询，恢复页必须在重启前说明从部署日志查看失败原因，不能承诺半启用状态下网页仍可用。

首次支持当前标准单 `/data` 持久化挂载，暂存与目标在同一文件系统。目标目录额外挂载导致改名失败时保留现场和具体错误，不静默改成边复制边启动的方案。

CLI 密码重置在打开数据库前及实际写事务前检查是否处于 activating。这样可防止刚发布的数据库被 CLI 改密后，又在启用重试时覆盖；准备中的空实例仍按现有“尚未初始化”处理。这里不建立通用文件锁，也不干预外部管理工具。

## 9. 版本与打包

现 `package.json` 的 `0.1.0` 不是可靠发布版本。已通过 `scripts/build-metadata.mjs` 将构建时显式传入的 `ARISO_BUILD_VERSION` 与 `ARISO_BUILD_REVISION` 写入 `dist/build-info.json`，随 standalone 和镜像打包；发布工作流向两个架构传入同一身份。版本须为 `v` 前缀 semver（可带预发布标识），revision 为 40 位小写十六进制提交 SHA。两项缺一或格式错误使构建失败；都未设置时写入 null，正常应用可用但不开放备份/恢复创建。启动时只补环境变量不会改变已有构建身份。不让备份身份依赖构建路径、临时目录、镜像上传时间或额外签名。

manifest 保存该发布版本和数据库迁移版本。第一版只在相同应用版本、完整 revision 和迁移版本下恢复，之后按现有升级流程升级；不支持降级。本地端到端验证必须显式使用预发布标识，不把含工作区未提交改动的构建称为正式 release；示例见[验证指南](../docs/guides/verification.md#备份与恢复的构建身份)。

工作线程使用编译后的独立入口 `dist/cli/backup-worker.js`。加入现有 `scripts/package-standalone.mjs` 的明确追踪入口，验证其库及传递依赖都被打包。不能只在开发目录有 node_modules 时通过。

## 10. 内部接口

接口只服务管理界面，不加入公开上传 API。沿用 `{ code, message, fields? }` 错误格式及 no-store；状态接口不返回密码、凭据或任意宿主绝对路径。诊断日志保留非敏感的真实路径和提供方错误。

### 已初始化站点

| 接口                              | 行为                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| `GET /api/backups?cursor=&limit=` | 所有者查看真实范围、空间估算、构建可用性及任务历史，分页                                  |
| `PUT /api/backups/:id`            | 所有者创建任务，body 为 password；客户端为一次意图生成固定 UUID，网络不明时先 GET 同一 ID |
| `GET /api/backups/:id`            | 阶段、计数、字节、错误、是否可下载                                                        |
| `POST /api/backups/:id/cancel`    | 请求取消；重复取消返回当前状态，不直接宣布已经退出                                        |
| `GET /api/backups/:id/file`       | ready 文件下载；HEAD 返回元信息；普通附件流，不持有内容冻结                               |
| `DELETE /api/backups/:id`         | 删除终态任务及其文件；活动/正在下载返回明确冲突                                           |
| `GET /api/backups/activity`       | 所有者页面读取修改暂停状态、阶段与当前任务 ID                                             |

同一个 ID 的创建重复请求统一返回 409，调用者读取现状，不因为新 body 不同而悄悄替换密码或生成第二份文件。不同 ID 在已有活动备份时也返回 409。不引入通用幂等账本。

### 空白实例

以下请求全部要求当前初始化码，并验证实例仍未初始化。targets 接口已接入，公开类型见 `src/server/backup/restore-remote-types.ts`：

| 接口                                                  | 行为                                                                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/setup/restore`                              | 已授权查询当前任务；没有任务返回空状态                                                                                   |

| `POST /api/setup/restore/:id/targets/:storageId/test` | 接收 revision 及可选的 R2 无锁确认；202 后通过 GET 读取 testing/passed/failed，测试当前新位置，不依赖原 S3               |
| `POST /api/setup/restore/:id/execution`               | 开始或从失败阶段显式重试；同一任务不并发执行                                                                             |
| `POST /api/setup/restore/:id/cancel`                  | 取消并停止任务，列出本次残留目标，保留明确清理结果                                                                       |

请求超时并不等于服务端失败。前端按同一任务 ID 查询，不自动创建新任务或重复开始。上传、解密、复制、ready 与重启启用分别表达；恢复启用不是一个允许已初始化站点调用的 Web 覆盖接口。

## 11. 实现顺序与完成条件

详见任务清单。实施顺序是：隔离格式/启用实验 → 暂停基础和写入口接入 → 本地完整闭环与已认可界面对接 → 本地回归和发布形态验证 → S3 源读取、目标配置、复制及界面接入。当前进入 S3 提供方、浏览器和故障复核，不能把本地历史通过概括为完整产品验收完成。

每一步保留现有应用可运行。新备份入口在写入矩阵与后台暂停全部接通前不对外启用；没有额外用户配置型 feature flag。前置能力通过真实临时目录/数据库测试，不在产品页面留假的成功状态。

必须证明：原服务器和原 S3 不可访问时恢复仍成功；备份期间浏览及临时预览真实可用；密码/截断/空间不足/中断均不会启用半成品；同 bucket 其他前缀不被删除；原 ID、关系、账号与既有链接身份保留。
